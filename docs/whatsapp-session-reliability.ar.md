# موثوقية جلسة WhatsApp — 1.0.1

تاريخ التحقيق: 3 نوفمبر 2026. قاعدة إصدار الإصلاح: `main` عند commit `cf84a6b` (الإصدار 1.0.0). يحتوي هذا الإصدار على إصلاحات WhatsApp فقط؛ لا يتضمن تعديلات فرع الفواتير `64a125b`.

## النتيجة وحدود الدليل

هناك أخطاء مؤكدة في حذف جلسة مفتوحة وإدارة المتصفح والتهيئة. تم إصلاحها في كود التطبيق واختبارها. لا تثبت مقتطفات إنتاج العميل لماذا بدأت أول إشارة logout: هل ألغى WhatsApp الجهاز المرتبط، أم حدث logout من الهاتف، أم أصدر عميل الويب الإشارة لسبب آخر. لا يمكن استعادة اعتماد ألغاه WhatsApp بمجرد إعادة الملفات، ولا يمكن ضمان عدم الاحتياج إلى QR مستقبلًا.

نجاح الاستعادة بعد إعادة التشغيل الأولى يثبت أن مسار LocalAuth كان قابلًا للحفظ والاستعادة وقتها، وليس أن الاعتماد ظل صالحًا في اليوم التالي.

## الأسباب المؤكدة بالملفات والأسطر

الأسطر التالية تخص الملفات المثبتة فعلًا بإصدار `whatsapp-web.js 1.34.7` و`puppeteer 25.16.0`، المقفولين في package-lock.json، دون تعديل node_modules:

1. `node_modules/whatsapp-web.js/src/Client.js:495–503`: مع كل `framenavigated`، إذا احتوى عنوان الإطار على `post_logout=1` **أو** كانت `lastLoggedOut=true`، يرسل `disconnected('LOGOUT')` ثم يستدعي `authStrategy.logout()` عند **498** قبل إغلاق Chromium. لا يستدعي هذا الفرع logout لمجرد TIMEOUT.
2. `Client.js:390–421`: يتم تعيين `lastLoggedOut=true` بواسطة `onLogoutEvent` المرتبطة بإشارتي `WAWebCmd`، وهما `logout` و`logout_from_bridge`. المقتطف المقدم من الإنتاج لا يميز أي شرط من الشرطين فعّل السطر 498.
3. `node_modules/whatsapp-web.js/src/authStrategies/LocalAuth.js:56–66`: `logout()` ينفذ `fs.promises.rm(userDataDir, {recursive:true, force:true, maxRetries:4})`. حذف مجلد بروفايل مفتوح على Windows يفسر `EBUSY ... unlink .../lockfile`. الحذف المتكرر قد يحذف بعض الملفات قبل التعثر بملف مقفول؛ لا توجد نسخة من مجلد العميل تثبت مقدار الحذف الفعلي.
4. `Client.js:125–147` ينتظر `Debug.VERSION` ثم يقرأ `WAWebSocketModel.Socket` بلا اختبار جاهزية الوحدة. وكذلك `src/util/Injected/AuthStore/AuthStore.js:5`. تم إعادة إنتاج `Socket=null` في Chromium فعلي مع `ExposeAuthStore` المثبتة، والتحقق من أن adapter ينتظر الجاهزية. لا نملك دليلًا يحدد سبب غياب الوحدة عند العميل: تحميل جزئي، توقيت تنقل الصفحة، أو عدم توافق واجهة WhatsApp احتمالات وليست نتائج مؤكدة.
5. `package.json:51–54` يفرض Puppeteer 25.16.0؛ `Client.js:1277–1283` يستخدم `browser?.isConnected?.()` ليقرر الإغلاق. المثبت لدينا يملك `connected` بدل `isConnected()`؛ انظر `node_modules/puppeteer-core/lib/puppeteer/cdp/Browser.js:448`. اختبار Chromium حقيقي أثبت أن `Client.destroy()` الأصلية ترجع مع متصفح متصل، بينما adapter يغلقه. هذا مسار مؤكد لبقاء متصفح بعد destroy، وليس إثباتًا بأنه بدأ logout عند العميل.
6. المسار العام للحالات غير المقبولة في `Client.js:824–853` يستدعي `authStrategy.disconnect()` وdestroy. `BaseAuthStrategy.disconnect()` فارغة ولا تحذف LocalAuth. لذلك لا يصح تفسير كل disconnected بأنه حذف جلسة.

مراجع أصلية مساعدة: [مصدر Client](https://docs.wwebjs.dev/Client.js.html)، [مصدر LocalAuth](https://docs.wwebjs.dev/authStrategies_LocalAuth.js.html). أرقام الأسطر أعلاه من النسخة المحلية المثبتة، لا ترقيم صفحة HTML.

هذه أرقام الأسطر في commit `cf84a6b` على main، وليست أرقام الملفات المعاد تنظيمها الآن (ملفا العامل وBridge مطابقان لما تم فحصه أولًا):

|---|---|
| `apps/whatsapp-worker/index.ts:49–61, 253–256, 349–353` | SIGKILL/taskkill قبل محاولة الإغلاق الطبيعي، بما يهدد تفريغ بيانات Chromium إلى القرص. |
| `apps/whatsapp-worker/index.ts:117–155` | قفل exists/read/write غير ذري، مع تجاهل أخطاء كتابته وحذف Singleton دون إثبات غياب المتصفح. |
| `apps/whatsapp-worker/index.ts:194–216` | سبب الفصل وسبب auth_failure لا يسجلان؛ QR callback غير محمي من نتيجة متأخرة. |
| `apps/whatsapp-worker/index.ts:230–249` | initialize خارج طابور الأوامر؛ catch تستخدم client العامة وقد تنظف جيلًا آخر بعد disconnect/connect. |
| `apps/server/whatsapp-bridge.ts:58–74, 133–142` | watchdog كل 15 ثانية + مؤقت بعد خروج العامل، بلا ميزانية نهائية أو backoff موحد. |
| `apps/server/whatsapp-bridge.ts:36–44` | قتل PID قديم بمجرد أن اسم العملية chrome.exe، دون إثبات أنها تملك البروفايل. |
| `apps/server/whatsapp-bridge.ts:166–180` | مهلة 5 ثوان قبل فرض قتل شجرة العمليات. |

هذه عيوب مثبتة بالفحص، ويمكنها تضخيم الفشل أو منع الاسترداد. لا نملك ترتيب أحداث كاملًا من جهاز العميل لإسناد الحادث الأول إلى عيب واحد بعينه.

## التغييرات المنفذة

- `apps/whatsapp-worker/reliable-client.ts`: adapter مملوك للتطبيق، مع تحقق من إصدار المكتبة عند تشغيل العامل. يمنع حذف LocalAuth من داخل متصفح حي، ويغلق Chromium باستخدام API الصحيحة، وينتظر وحدات المصادقة بفحص كل 200ms لمدة 30 ثانية. يجمع الحقن المتزامن ويحوّل أخطاء الحقن، بما فيها أخطاء تنقل لاحق، إلى حدث استرداد معالج.
- `apps/whatsapp-worker/session.ts`: كل جيل يمتلك client/initialization/timers/profile. callbacks القديمة لا تغير الجيل الجديد. مهلة أولية 120 ثانية، وأخرى بعد authenticated. تبديل الحالة أثناء التنظيف يمنع عمليات إرسال جديدة. فحص صحة كل 15 ثانية مع مهلة 5 ثوان و60 ثانية للحالة المتدهورة قبل الاسترداد.
- `packages/runtime/whatsapp-profile.ts`: قفل حصري SQLite خارج مجلد Chromium في `whatsapp-auth/.locks/<company>.sqlite`. يعتمد على أقفال نظام التشغيل ويتحرر تلقائيًا بعد موت العامل أو reboot؛ لا نحذف ملف القفل للتغلب على مستخدم نشط. يمنع العامل القديم أثناء الانتقال، ويتعرف على metadata من boot سابق.
- قبل فتح البروفايل، وبعد إغلاقه، يتم فحص العمليات حسب **مسار user-data-dir الكامل**. على Windows: CIM ثم taskkill فقط لعملية تم التحقق منها، مع إعادة الفحص قبل القتل. لا توجد عملية قتل باسم chrome فقط أو اعتماد على PID محفوظ قد أعيد استخدامه. Singleton metadata تزال فقط بعد حيازة القفل وإثبات غياب مالك متصفح؛ ملفات الاعتماد وDefault/lockfile لا تزال يدويًا.
- الإغلاق الطبيعي يسبق القوة. ننتظر اكتمال initialize ونثبت غياب عمليات البروفايل قبل تحرير القفل. إذا لم تستقر التهيئة، يفشل التنظيف ويخرج العامل؛ القفل يتحرر من النظام، والعامل التالي يتحقق من المتصفح اليتيم. العامل له حد إغلاق 35 ثانية، والخادم يسمح بـ40 ثانية قبل فرض الإنهاء.
- `LOGOUT` و`UNPAIRED` و`UNPAIRED_IDLE` وauth_failure تكتب علامة تحتاج ربطًا جديدًا خارج البروفايل. الاسترداد التلقائي يتوقف، حتى بعد إعادة تشغيل التطبيق. طلب الربط اليدوي فقط ينقل المجلد القديم إلى `.revoked-<company>-<time>` بعد إغلاق المتصفح، ثم يبدأ QR. علامة الربط ترفع بعد ready. الانقطاع العادي لا ينقل ولا يحذف مجلد الجلسة.
- `CONFLICT` وحالات الحظر/الإصدار تتوقف لعرض سبب يستدعي تدخلًا. لا يوجد takeover أو تغيير User-Agent.
- `apps/server/whatsapp-bridge.ts` و`packages/runtime/whatsapp-recovery.ts`: طلبات الاتصال المتزامنة تستخدم وعدًا واحدًا، ويحجز معرف الشركة قبل وصول أول state. مؤقت استرداد واحد بثماني محاولات إضافية: 2، 4، 8، 16، 32، 60، 60، 60 ثانية؛ الميزانية تصفر بعد ready مستقرة 60 ثانية أو طلب يدوي. عمليات العمل والإرسال لا تعاد تلقائيًا.
- سجلات JSON تتضمن reason والـPID والخروج والإشارة ومحاولة الاسترداد وأسباب فشل التهيئة المنقحة. يسجل توليد QR دون محتواه؛ لا تسجل مفاتيح LocalAuth أو cookies أو بيانات auth events. يسجل LOGOUT هل شوهد `post_logout=1` وهل كانت إشارة bridge موجودة دون عنوان الصفحة.
- `/healthz` يعرض reason وrequiresReauth وrecoveryBlocked وretryAttempt. الواجهة تعرض reconnecting كحالة اتصال.
- إصدار مستقل `1.0.1` في package/package-lock/المثبت، لأن `scripts/windows/update.ps1:13–19` يتجاوز تثبيت الإصدار النشط نفسه. مسار البيانات وAppId وهوية الخدمة والمخطط لا تتغير بهذا الإصلاح.

## الاختبارات والتحقق

| السيناريو | التحقق المتاح |
|---|---|
| إعادة تشغيل Windows بجلسة مربوطة دون QR | حفظ نفس المسار والبيانات بعد إغلاق/إعادة فتح Chromium مُختبر. reboot فعلي والجهاز المرتبط عند العميل يحتاجان تحققًا ميدانيًا. |
| انهيار العامل | عامل Node مستقل قُتل بالقوة؛ القفل تحرر والاعتماد التجريبي بقي. اختبار Bridge يحاكي الخروج ويثبت الاسترداد والحد الأقصى. اختبار المثبت الموجود يقتل عامل الخدمة ويتحقق من زوال المتصفح اليتيم وعودة عامل جديد. |
| انقطاع الإنترنت | اختبار انقطاع TIMEOUT دون حذف بيانات، وChromium فعلي بـoffline mode ثم استرداد نفس البروفايل. اتصال WhatsApp المربوط الحقيقي أثناء قطع الإنترنت غير متحقق محليًا. |
| انهيار Chromium | قتل Chromium حقيقي ثم إعادة فتح نفس البروفايل، مع بقاء قيمة localStorage سبق حفظها، وسبب CHROMIUM_DISCONNECTED. |
| تحديث التطبيق | نفس مسار auth مستخدم بعد إعادة إنشاء المشغل، وإصدار المثبت مميز. تثبيت وترقية Windows يخضعان لبوابة CI الموجودة؛ جلسة العميل الخاصة تحتاج تجربة ميدانية. |
| اتصال متزامن | منع مالكَي بروفايل بعمليتين، وتوحيد اتصال Bridge وحجز الشركة قبل أول state. |
| logout حقيقي | محاكاة إشارة المكتبة واستخدام LocalAuth الحقيقية: لا حذف حي، علامة دائمة، منع إعادة المحاولة، وأرشفة فقط بطلب يدوي. الإلغاء من هاتف حقيقي لم ينفذ. |
| ملفات مقفولة | backoff ونجاح بعد EBUSY وفشل ظاهر بعد نفاد الحد. اختبار Windows خاص يمسك FileStream بـFileShare.None ويشترط رصد محاولة إعادة فعلية قبل تحرير المقبض؛ يتخطى على Linux. |
| عدم توافق destroy | Chromium فعلي يثبت بقاء المتصفح مع upstream ثم إغلاقه مع adapter. |
| Socket=null | استدعاء ExposeAuthStore المثبتة يفشل في Chromium على fixture؛ adapter ينتظر تحميل الوحدة وينجح. |
| إغلاق فاشل | Chromium فعلي مع destroy يفشل: ينتهي المتصفح المملوك ويبقى متصفح مستقل آخر يعمل. |

الأوامر المحلية: `npm run typecheck`، `npm run test:core`، `npm test`، `npm run build`، `CHROME_NO_SANDBOX=true npm run test:whatsapp:browser`، `CHROME_NO_SANDBOX=true node tests/worker-smoke.mjs`. متغير تعطيل sandbox مستخدم لاختبارات Linux داخل بيئة التطوير فقط؛ Windows يحتفظ بالـsandbox. اختبار QR يتصل بخدمة WhatsApp ببروفايل مؤقت جديد، دون مسح QR أو ربط حساب أو إرسال رسائل.

نتائج التشغيل النهائية وتفاصيل CI توثق في `release-validation-1.0.1.ar.md`؛ لا تعد الاختبارات الصناعية بديلًا عن حساب مرتبط فعليًا.

## النشر والتحقق عند العميل

نعم، يلزم بناء Setup.exe جديد وإجراء Upgrade حتى يعمل كود العامل الجديد على Windows. لا يكفي رفع Git أو استبدال JavaScript داخل release نشط بنفس الرقم. المسار الموصى به هو workflow `Build Windows x64 Installer` على فرع الإصلاح؛ يبني الحزمة ويختبر التثبيت والترقية قبل اعتماد الملف. لا تنشر tag/إصدارًا عامًا قبل نجاح بوابة Windows.

1. احتفظ بسجل الحالة السابقة وقائمة الأجهزة المرتبطة في الهاتف، دون مشاركة QR أو مفاتيح أو نسخة auth في سجل عام.
2. استخدم Upgrade المعتاد؛ السكربت يوقف الخدمة وينشئ backup غير متصل قبل تفعيل release الجديد. لا تحذف ProgramData أو whatsapp-auth يدويًا.
3. تحقق من `/healthz` ورقم الإصدار، ثم ready بنفس الحساب. أعد تشغيل Windows، واقطع الشبكة وأعدها، وراقب سبب الفصل والتعافي. اختبر قتل العامل والمتصفح في بيئة تجريبية أولًا.
4. إذا كانت الحالة requiresReauth، راجع سبب LOGOUT وأحداث الجهاز المرتبط. قد يلزم مسح QR مرة جديدة إذا أُلغي الاعتماد بالفعل أو حُذف جزئيًا قبل الإصلاح.

المخاطر المتبقية: WhatsApp يستطيع إلغاء الربط أو تغيير وحداته الداخلية؛ قفل antivirus/قرص دائم يتطلب معالجة السبب بعد انتهاء المحاولات؛ metadata قديمة تالفة أو PID حي من نفس boot لا يمكن إثبات ملكيته تتوقف بأمان بدل انتزاع القفل؛ فشل CIM/الصلاحيات يمنع الاسترداد ويحتاج سجلات Windows؛ الأرشيفات الملغاة قد تحتوي اعتمادًا حساسًا وتبقى تحت صلاحيات مجلد الحالة ولا تُرفع للدعم. لا تُحذف تلك الأرشيفات تلقائيًا في هذا الإصلاح.
