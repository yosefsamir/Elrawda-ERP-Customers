# خطة تنفيذ تقارير الإدارة وشجرة فلاتر الأصناف والفروع

خطة بتاريخ 11 نوفمبر 2026، بناءً على مخطط ERP الفعلي وفحص النسخة المحلية ومطابقات المستخدم. هذه خطة التنفيذ وليست إعلانًا عن صفحات جاهزة.

## 1. النتيجة المطلوبة

إنشاء **بوابة تقارير مستقلة عن صفحة الأدمن الحالية**، لها صفحة دخول باسم مستخدم وكلمة مرور، تتيح اختيار مجموعة أصناف عند أي مستوى من شجرتها، واختيار فرع أو عدة فروع أو جميع الفروع، ثم تحليل مبيعاتها ورصيدها خلال فترة ومقارنتها بين الفروع. تدعم عدة مستخدمين، وينشئ الأدمن الحسابات ويعين كلمات مرورها من صفحة إعدادات البوابة داخل الأدمن.

الهدف النهائي الذي حدده المستخدم لاحقًا: **مقارنة رصيد المخزن الرئيسي بمبيعات وأرصدة الفروع، وإعداد احتياج توزيع أسبوعي لكل فرع**. الأولوية الحالية تثبيت الأساس والتقارير؛ تجهز مفاتيح البيانات وفصل الحسابات لخدمة هذا الهدف دون إدخال التنبؤ والتوزيع الآلي في التسليم الأول. خارطة الانتقال لهذا الهدف موضحة في القسم 13.

نفهم «اختيار أي فرع في الشجرة وتكميله» بأنه اختيار أي عقدة/مستوى من تصنيف الأصناف ومواصلة التصفية تحته، وليس إنشاء أو تعديل تعريفات ERP. يضاف حفظ الاختيارات باسم لإعادة استخدامها.

تعمل البوابة على **نفس مستمع وبورت البورتال الحالي**، الافتراضي 3212، بمسار مستقل `/reports/`. تبقى `/` للاستعلام عن المنتجات و`/manage` لإدارة الصور. الأدمن الحالي، الافتراضي 3211، يدير إعدادات التقارير وحساباتها فقط؛ لا توضع شاشات التقارير داخله. جلسات مستخدمي التقارير مستقلة عن جلسات الأدمن ومديري الصور، حتى مع اشتراكها في نفس البورت.

الهوية البصرية للشركة والموبايل متطلبان أساسيان من بداية التنفيذ. تنظيم الكود يكون كتطبيق واجهة مستقل ووحدات سيرفر مستقلة، لأن هذا الجزء متوقع أن يتوسع كثيرًا. تجهيز النشر الخارجي الفعلي يظل مرتبطًا بإعداد الدومين/النفق الموجود، ولا يحتاج فتح بورت جديد أو نشر الأدمن للعامة.

## 2. الشاشات المقترحة

### أ. أداء الأصناف — أول شاشة للتنفيذ

أعلى الصفحة: الفترة، اختيار الفروع والمخازن، محدد الأصناف، ثم «عرض التقرير»، «إعادة ضبط»، «حفظ الفلتر»، «تصدير CSV».

بعد تنفيذ البحث تظهر خلاصة النطاق: «1–27 أكتوبر / المنصورة والزرقا / ملابس ← بنطلون ← جبردين». تبقى الفلاتر قابلة للطي أثناء قراءة النتائج.

بطاقات الملخص: كمية البيع، مرتجع البيع، صافي المباع، المتبقي بنهاية الفترة، وعدد الأصناف المطابقة وعدد الأصناف بلا بيع. يوضح العنوان دائمًا أن رصيد الفترة التاريخية ليس رصيد اليوم.

على الكمبيوتر يكون العرض جدولًا، سطر لكل صنف تفصيلي/فرع/وحدة، مع إمكانية توسيعه حسب المخازن. على الهاتف تكون النتيجة بطاقة مختصرة لكل صنف، مع فتح الأرقام والحركة تفصيليًا دون الحاجة لجدول عريض:

| هوية الصنف | الموقع | الحركة والرصيد | الأداء |
| --- | --- | --- | --- |
| الكود الرقمي والخاص، القسم والتصنيف والوصف | الفرع؛ وتفاصيل المخزن عند التوسيع | افتتاح، وارد، تحويل وارد، مباع، مرتجع بيع، تحويل صادر، حركات أخرى، متبقي | نسبة التصريف، أيام التوفر/النفاد، معدل البيع، أيام تغطية الرصيد |

تُعرض الأعمدة الأساسية افتراضيًا، وتفتح الأعمدة التفصيلية من «الأعمدة» حتى لا تصبح الشاشة مزدحمة. لا تخفى التحويلات الصادرة أو الحركات الأخرى داخل رقم البيع.

ترتيب بالبيع أو التصريف أو المتبقي؛ فلتر «الكل / بلا بيع / رصيد موجب / نفد خلال الفترة». إظهار الأصناف ذات المخزون أو الحركة وبلا مبيعات أساسي، ولا يبدأ التقرير من جدول البيع وحده.

### ب. مقارنة الفروع

نفس الفلاتر، مع سطر ملخص لكل فرع. يعرض الكميات والمرتجعات وصافي البيع والمتبقي وعدد الأصناف بلا بيع. ضغط الفرع يفتح أداء أصنافه مع الاحتفاظ بالفترة ومحددات الأصناف.

داخل شاشة الأصناف يتوفر وضع «مقارنة الفروع» يضع نفس الصنف في صفوف متجاورة حسب الفرع على الكمبيوتر، وبطاقات فروع أو اختيار فرعين للمقارنة على الهاتف، بدل توسيع مصفوفة غير قابلة للقراءة.

القيم المالية لا تُعرض على أنها صافي مبيعات معتمد قبل تثبيت الخصومات والضريبة والتحصيل والعملة؛ المطابقات الحالية تخص الكميات والأرصدة. إضافة القيمة المالية جزء لاحق واضح من خطة التقارير بعد مطابقة فاتورة عادية وأخرى ذات خصم/مرتجع، دون تأخير شاشة أداء الكميات.

### ج. تفاصيل حركة الصنف

تفتح من صف النتيجة كصفحة فرعية أو لوحة جانبية: تعريف الصنف، الفرع والمخزن، افتتاح الفترة، ثم التاريخ ونوع الحركة ورقم المستند والداخل والخارج والرصيد المتتابع، والنهاية. تستخدم نفس محرك الحساب ومحددات التقرير.

لا نحتاج أسماء العملاء أو هواتفهم لهذه الشاشة. إذا اتسعت فترة الحركة أو كثرت المستندات تستخدم صفحات نتائج. الرجوع يعيد المستخدم لموضعه وفلاتره السابقة.

### د. تسجيل الدخول وحساب المستخدم — داخل بوابة التقارير

صفحة `/reports/login` بشعار الشركة واسمها واسم المستخدم وكلمة المرور وإظهار/إخفاء كلمة المرور ورسالة خطأ واضحة. لا يوجد تسجيل ذاتي؛ الأدمن ينشئ الحساب. بعد الدخول ينتقل المستخدم لأداء الأصناف، مع قائمة مناسبة للهاتف تضم التقارير والفلاتر المحفوظة وإعدادات العرض والحساب وتسجيل الخروج. إعدادات المستخدم تقتصر على تفضيلاته، ولا تتيح إنشاء مستخدمين أو تغيير إعداد SQL أو هوية الشركة.

### هـ. إعدادات بوابة التقارير والمستخدمين — داخل الأدمن الحالي

صفحة مستقلة بالأدمن تشمل تفعيل/تعطيل بوابة التقارير، رابط فتحها، ربطها بالشركة/المصدر الحالي، وإعدادات الهوية والعرض الخاصة بها. قسم المستخدمين يعرض اسم المستخدم والاسم الظاهر والحالة وتاريخ الإنشاء وآخر دخول، ويتيح إضافة مستخدم وتعيين أو إعادة تعيين كلمة مروره وتعطيله/تفعيله وإنهاء جلساته. كلمات المرور لا تعرض أو تسترجع؛ عند الحاجة يعين الأدمن كلمة جديدة. يمكن إتاحة «كل الفروع أو فروع محددة» لكل حساب؛ نطاق التقرير دائمًا داخل الفروع المسموحة له.

## 3. شجرة الأصناف: السلوك المحدد

التسلسل المثبت من ERP:

**النوع ← القسم ← التصنيف ← المقاس/الوصف ← كود الموديل ← الصنف التفصيلي/الوحدة**.

| اسم المستوى في الواجهة | المصدر |
| --- | --- |
| النوع | `kind.idkind / fkind` ضمن البرنامج |
| القسم | `main.idname / fname` |
| التصنيف | `maincolor.idcolor / fcolor` |
| المقاس/الوصف | `mainsize.idsize / fsize` |
| كود الموديل | `mainfarz.idfarz / ffarz` |
| الصنف والوحدة | `maindet.iddet` و`mainunits.idunit` |

الأسماء التشغيلية مأخوذة من صورة المستخدم؛ لا يُعاد تفسير عمود اللون باعتباره لونًا فعليًا. عرض الصنف النهائي يضم الاسم/الوصف والكودين والوحدة، لأن الكود الخاص قد يكون `*` أو يتكرر.

المحدد يتكون من «قوائم مترابطة» للاختيار السريع و«تصفح الشجرة» للاختيار المتعدد؛ الاثنان يعكسان نفس حالة الاختيار:

1. اختيار نوع يجعل قائمة الأقسام تعرض أبناءه فقط؛ القسم يحدد التصنيفات، والتصنيف يحدد المقاسات/الأوصاف، وهكذا.
2. يمكن التوقف عند أي مستوى: اختيار «ملابس» يشمل جميع أصنافه، واختيار «بنطلون» يشمل كل تصنيفاته، دون إجبار المستخدم على تحديد كود.
3. بحث شامل بالاسم أو الوصف أو الكود الرقمي أو الخاص. كل نتيجة تعرض مسارها كاملًا؛ اختيار قسم من البحث يثبت آباءه آليًا ثم يتيح متابعة أبنائه، ولا يلزم البدء بالنوع.
4. يمكن تحديد عدة عقد من فروع مختلفة في نفس الشجرة: «بنطلون ← جينز» و«صيفي 2026 ← تيشيرت» مثلًا، أو عدة أكواد بعينها.
5. اختيار عقدة يشمل أبناءها. مربع الأب يكون محددًا عند اختيار الكل، وجزئيًا عند اختيار بعض الأبناء. فتح/طي العقدة إجراء مستقل عن تحديدها.
6. يمكن اختيار قسم كامل واستبعاد تصنيف أو صنف منه. الاختيارات تظهر كبطاقات صغيرة مع مساراتها، والاستثناءات ظاهرة باسم «مستبعد».
7. عند تغيير مسار الأب في وضع القوائم، تزال اختيارات الأبناء التي لا تنتمي إليه في المسار الجاري فقط، مع إشعار صغير. الاختيارات الأخرى المثبتة كمسارات مستقلة لا تمسح دون قصد.
8. الفلتر على الهوية وليس النص: قسمان بنفس الاسم تحت نوعين مختلفين يبقيان عقدتين منفصلتين. البحث الجزئي يساعد على الوصول، لكن التقرير ينفذ بالمعرف المختار.
9. لا تخفى عقدة لأنها لم تبع خلال الفترة. شجرة التعريف مستقلة عن سجل البيع؛ «بلا بيع» نتيجة تحليل مقصودة.
10. يحتفظ المصدر بالقيم الأصلية؛ التسامح مع حالة الحروف/الفراغات في البحث لا يدمج صنفين ولا يسقط الأصفار من الأكواد.

دلالة الاختيار على السيرفر: اتحاد الأصناف الواقعة تحت العقد المضمنة، ناقص اتحاد الأصناف تحت العقد المستبعدة، مع إزالة التكرار. اختيار الأب والابن لا يضاعف المبيعات. الاستثناء له الأولوية داخل النطاق المختار. الواجهة تعيد تنظيم الاختيارات عند إعادة تحديد عقدة مستبعدة حتى لا يبقى تعارض مخفي.

«كل الأصناف» وضع صريح؛ لا تعني قائمة اختيارات فارغة تلقائيًا اختيار الكل. إذا اختار المستخدم وضع «محدد» دون عقد، يظهر طلب تحديد أصناف بدل تشغيل تقرير واسع بالغلط.

## 4. اختيار الفروع والمخازن

- محدد متعدد قابل للبحث، مع «كل الفروع» و«تحديد فروع» و«إلغاء التحديد»، ويعرض عدد الفروع المختارة.
- «كل الفروع» يعني كل الفروع المتاحة في نطاق تقارير الشركة/البرنامج وقت تشغيل التقرير، وليس قائمة العملاء التسعة الثابتة ولا الفروع التي لها مجموعات WhatsApp فقط.
- تعرض الفروع المحذوفة/غير النشطة، عند وجودها وتحقق صلاحية إظهارها، داخل خيار «تضمين الفروع غير النشطة» لتقارير الماضي؛ لا تسقط الحركات التاريخية بصمت ولا تخلطها مع الفروع التشغيلية الافتراضية.
- المخازن تأتي تحت فروعها وتعرف بالمفتاح `(program,branch,store)`. نفس رقم المخزن في فرعين ليس مخزنًا واحدًا.
- الافتراضي «كل مخازن الفروع المحددة». إزالة فرع تزيل مخازنه من الاختيار. إذا حدد المستخدم مخازن ثم أضاف فرعًا جديدًا لا ندخل مخازنه إلى نطاق «مخازن محددة» بصمت.
- اختيار أكثر من فرع يتيح «فصل حسب الفرع» افتراضيًا و«إجمالي الفروع المختارة». لا يحتاج المستخدم لتغيير شجرة الأصناف عند تغيير الفرع.
- النطاق المسموح يثبت على السيرفر في كل طلب. «الكل» لا يتجاوز نطاق الشركة أو أي سياسة فروع تضاف لاحقًا.

## 5. الفترات وحفظ الفلاتر وتجربة الاستخدام

- من/إلى شاملان للمستخدم، مع اختصارات: اليوم، أمس، آخر 7 أيام، الشهر الحالي، الشهر السابق. الحساب يستخدم نهاية اليوم التالي حدًا حصريًا.
- الافتراضي الشهر الحالي حتى اليوم بحسب القاهرة؛ عند تجربة نسخة أكتوبر تظهر بوضوح أنها نسخة محلية بتاريخها، وتستخدم فترة 1–27 أكتوبر للمطابقة بدل الإيحاء بأنها بيانات حية.
- البداية لا تتجاوز النهاية. التقارير السابقة لنقطة افتتاح موثوقة تعرض أن الرصيد غير متاح لتلك الفترة؛ لا يفترض تاريخ 1 أغسطس لكل قواعد ERP مستقبلًا.
- لا يعاد تحميل التقرير عند كل نقرة في الشجرة؛ «عرض التقرير» يطبق الاختيارات. أي تعديل بعد العرض يضع علامة «الفلاتر تغيرت — اعرض التقرير لتحديث النتائج».
- إذا تغيرت الفلاتر أو ترتيب النتائج أثناء طلب جارٍ، يلغى/يهمل الرد الأقدم فلا يستبدل أحدث نتيجة. تغيير نطاق الفلتر يعيد رقم الصفحة إلى البداية.
- فتح التقرير أول مرة لا يشغل استعلام مخزون ثقيل تلقائيًا. يوجد تحديث يدوي؛ التحديث التلقائي خيار قابل للتفعيل لاحقًا بعد قياس الحمل.
- حفظ الفلتر باسم، مع الفترة إما «آخر 7 أيام/الشهر الحالي…» كتعبير متحرك، أو تواريخ ثابتة. يملك كل مستخدم فلاتره ويمكنه إعادة تسميتها وحذفها.
- الفلتر المحفوظ مقيد بالشركة وهوية مصدر ERP والبرنامج. بعد تغيير المصدر لا تعاد مطابقة الأسماء أو IDs آليًا مع قاعدة مختلفة.
- إذا حذف تصنيف أو فرع محفوظ، تظهر العناصر غير المتاحة ويطلب تصحيح النطاق قبل التنفيذ؛ لا يستبدل الاختيار المفقود بوضع «الكل».
- اختيار أب محفوظ يشمل أبناءه الحاليين بعد تحديث التعريفات؛ تظهر زيادة/نقص عدد الأصناف عند تغيرها. إعدادات الفلتر تحفظ القصد «كل القسم»، وليس نسخة قديمة خفية من أكواده.
- واجهة عربية RTL، تعمل بلوحة المفاتيح، مع تسميات لمربعات الحالة الجزئية، وبحث واضح وإغلاق للنوافذ وإعادة التركيز لمكانه. على الهاتف تفتح الفلاتر والشجرة كلوحة كاملة؛ النتائج بطاقات قابلة للتوسيع، والجدول الأفقي عرض اختياري للأرقام التفصيلية وليس وسيلة الاستخدام الأساسية.

## 6. الحسابات وقواعد التجميع

1. المصدر حسابات الحركة الأصلية التي جرى فحصها، عبر طبقة قراءة SQL؛ لا قراءة من جداول حساب التكلفة المساعدة أو من SQLite الخاص بالعملاء.
2. تنقل قواعد التجربة من Python إلى TypeScript بمحرك مستقل قابل للاختبار. Python يبقى أداة فحص؛ لا يعتمد تشغيل إصدار Windows على تثبيت Python.
3. مستوى الحساب الثابت `(program,branch,store,product,unit)`. تعد الحركات مع مفتاح المستند الثلاثي، وتستبعد المحذوف من الرأس والتفاصيل، ويتسجل طرفا التحويل قبل تطبيق نطاق الفرع/المخزن على الأطراف. فلترة مصدر التحويل بالفرع مبكرًا ستفقد الوارد من فرع آخر.
4. تحسب نقطة الافتتاح وتاريخ أثر كل نوع حركة من المصدر. البيع والمرتجعات وإشارات الكمية تبقى موقعة؛ لا يحول المستخدم رصيدًا سالبًا إلى مرتجع بيع افتراضي.
5. **سياسة المستخدم:** الافتتاح والنهاية السالبان يظهران صفرًا، وتبقى القيم الأصلية وتسلسل الحركات داخليًا. لا يصفر الرصيد بعد كل حركة حتى لا يتحول توريد يغطي عجزًا سابقًا إلى مخزون وهمي. الحالات السالبة لا تعطل العمل.
6. تطبق سياسة الصفر عند مستوى الحساب الثابت، ثم تجمع الأرصدة المعروضة للفروع/الأقسام؛ لا يعوض عجز صنف أو مخزن رصيد صنف أو مخزن آخر في الإجمالي. الأرقام المعروضة بعد التصفير قد لا تحقق معادلة افتتاح + حركة = نهاية؛ سجل الحركة الأصلي هو مرجع المعادلة.
7. صافي المباع = البيع − مرتجع البيع. المتاح الأساسي = الافتتاح المعروض + التوريد الداخل + التحويل الوارد. التصريف = صافي المباع ÷ المتاح الأساسي. لا يضاف المرتجع للمقام مرة ثانية، والتحويل الصادر ليس بيعًا.
8. أيام التوفر تعاد من الرصيد الموقع خلال الفترة. السالب والصفر كلاهما غير متاح. القياس اليومي تقريبي؛ لا تدعى دقة ساعات النفاد أو ترتيب حركات لها نفس الوقت.
9. معدل البيع أثناء التوفر وأيام التغطية يعرضان عند مستوى صنف/فرع/وحدة، وتظهر مدة النفاد وحجم العينة حتى لا يعني بيع قطعة واحدة نجاحًا مؤكدًا.
10. عند التجميع، نسبة التصريف من مجموع صافي المباع ÷ مجموع المقامات الصالحة، وليست متوسط نسب الصفوف. لا تجمع أيام التوفر أو متوسطات الأصناف وتعرضها كأنها أيام فرع واحد؛ تعرض هذه المؤشرات التفصيلية في صفوف الصنف فقط. يمكن عرض متوسط بيع المجموعة في اليوم بقسمة مجموع البيع على أيام الفترة تحت اسم مختلف واضح.
11. الوحدات المختلفة لا تجمع إلا بعد إثبات معامل التحويل. عند حالة غير مدعومة تعرض مؤشرات الرصيد «غير متاح» مع سبب محدد، ويمكن بقاء كمية البيع بحسب وحدتها؛ لا تنتج إجماليًا مكتملًا من صفوف مستبعدة دون إظهار عددها.
12. لا نصنف تلقائيًا «ممتاز/ضعيف» بنسب ثابتة لكل الأقسام. يبدأ التقييم بأرقام وفرز ومقارنة؛ إضافة أهداف حسب القسم/الموسم قرار تجاري لاحق.

## 7. البيانات وواجهات API المقترحة

### تعريفات الفلاتر

`GET /api/reports/filter-options` يعيد البرنامج وهوية المصدر/إصدار تعريفاته والفروع والمخازن والأصناف مع IDs ومسارات الشجرة. في النسخة المفحوصة 1,169 صنفًا، لذا نبدأ بطلب تعريفات واحد محدود الحجم ونبني الشجرة من القيم الفريدة. إذا تجاوز الحجم المقاس الحد المناسب ينتقل التحميل للأبناء حسب الحاجة دون تغيير معنى الاختيار.

تعريفات فقط، دون تكاليف أو بيانات عملاء. Cache مقترح دقيقة واحدة مقيد بالشركة وهوية المصدر، ويلغى عند تغيير الاتصال. البحث الشامل يستطيع استخدام نفس التعريفات في البداية؛ لا نضيف اتصال SQL لكل حرف مكتوب بلا حاجة.

### طلبات التقارير

- `POST /api/reports/item-performance/query`
- `POST /api/reports/branch-comparison/query`
- `POST /api/reports/item-movements/query`
- `POST /api/reports/item-performance/export` لملف CSV بنفس النطاق.

مثال تقريبي لجسم الفلتر، مع تثبيت الشركة والبرنامج من إعدادات السيرفر لا من حقول موثوقة من المتصفح:

```json
{
  "period": {"from": "2026-10-01", "through": "2026-10-27"},
  "branches": {"mode": "selected", "ids": [39, 45]},
  "stores": {"mode": "all"},
  "items": {
    "mode": "nodes",
    "include": [{"level": "section", "id": "53004"}],
    "exclude": []
  },
  "groupBy": "product_branch",
  "page": 1,
  "pageSize": 50,
  "sort": {"field": "netSold", "direction": "desc"},
  "optionsVersion": "source-scoped-definition-version"
}
```

السيرفر يتحقق من العقد وانتمائها للبرنامج والشركة، ويحلها إلى أصناف تفصيلية بنفسه؛ لا يثق في IDs أوراق الشجرة الموسعة من العميل ولا في شروط SQL تأتي من الطلب. يحافظ على معرفات bigint كنصوص حيث يلزم، ولا يمررها إلى أرقام JavaScript غير آمنة.

الرد يتضمن: النطاق الذي طبق فعليًا، عدد الأصناف المطابقة، الصفوف، مجاميع كامل النتيجة وليس الصفحة، عدد النتائج، وقت القراءة ومدة الاستعلام، هوية/وصف المصدر، وسياسة السالب وحالات المؤشرات غير المتاحة. إذا تغيرت التعريفات التي يعتمد عليها الاختيار يطلب تحديثها بدل تطبيق نطاق مختلف بصمت.

الحفظ:

- `GET/POST /api/reports/saved-filters`
- `PUT/DELETE /api/reports/saved-filters/:id`

جدول SQLite محلي مقترح `report_saved_filters`: معرف، صاحب الفلتر من مستخدمي التقارير المستقلين، الشركة، هوية المصدر، البرنامج، الاسم، نسخة صيغة الفلتر، الفلتر، وتاريخا الإنشاء والتعديل. لا نخزن أرصدة أو نسخة دائمة من المستندات في هذا الجدول.

## 8. الأمان والأداء والتصدير

- مسارات قراءة التقارير تسجل كوحدة محمية داخل مستمع البورتال تحت `/api/reports/` بجلسة تقارير مستقلة. مسارات إعداد البوابة وإدارة حساباتها وحدها تسجل في تطبيق الأدمن تحت `/api/reporting-admin/` بجلسة `operators`. جلسة مدير الصور أو الأدمن لا تتحول تلقائيًا لجلسة تقارير، وجلسة التقارير لا تتيح إدارة الصور أو الأدمن.
- إعداد SQL يؤخذ من المصدر المحدد للشركة وجهاز السيرفر، دون fallback صامت لشركة/قاعدة أخرى. تغييره يغلق/يبطل pool وcache المصدر القديم.
- حدود على الفترة وحجم العقد المختارة والصفحة وعدد التصدير، واستعلامات بمعاملات وربط قوائم IDs آمن. بداية مقترحة: 50 صفًا، حد صفحة 100، فترة حتى 366 يومًا، وطلب ثقيل واحد جارٍ لكل جلسة؛ تضبط الحدود بعد القياس.
- فلترة الأصناف والبرنامج والحد الأعلى للتاريخ داخل SQL مبكرًا، لكن لا تقطع حركات ما قبل بداية التقرير اللازمة للافتتاح. تجمع الحركة يوميًا عند الحاجة لأيام التوفر بدل نقل كل المستندات للمتصفح.
- ترتيب ثابت مع مفتاح إضافي لكسر التعادل، ومجاميع مستقلة عن حدود الصفحة. لا نحسب مخزون النتيجة من الـ50 صفًا المعروضة فقط.
- التقرير لا يدخل حلقة تحديث الشركة الحالية كل 4 ثوانٍ؛ دورة تحميله مستقلة. pool محدود، مهلة، وإلغاء عند الإمكان أو تجاهل آمن للطلبات القديمة.
- يوضح وقت القراءة. التقرير متعدد الاستعلامات على مصدر يتغير لا يدعي لقطة متزامنة كاملة؛ يقلل عدد القراءات المتفرقة، ويستفيد من snapshot isolation إن كانت متاحة أصلًا دون تفعيل إعدادات ERP تلقائيًا.
- لا نضيف مؤشرات أو جداول أو إجراءات إلى ERP تلقائيًا. أي بطء يقاس أولًا، ثم نقرر إن كان التجميع المحلي المحدود أو cache قصير مناسبًا.
- المصدر المنقطع يعرض تعذر التحديث؛ آخر نتيجة إن بقيت ظاهرة تحمل وقتها وعلامة أنها سابقة، ولا تعرض كرصيد حديث.
- CSV بالعربية UTF-8، مع حماية الخلايا التي قد تعامل كصيغ في Excel، وتثبيت الأكواد كنص عند الإمكان. يصدر كامل النطاق ضمن حد معلن، لا الصفحة الحالية فقط. عند تجاوز الحد يطلب تضييق النطاق أو ينتقل لتصدير خلفي في مرحلة لاحقة، ولا يبتر الملف بصمت.
- حفظ الحسابات والجلسات والإعدادات والفلاتر يضيف migration محلية؛ تراجع حدود إصدار SQLite في الفتح والتحقق من النسخ الاحتياطية واختبارات الاستعادة معًا، لأن الإصدار الحالي 3. تتضمن النسخة الإعدادات والحسابات والهوية والفلاتر، وتلغى جلسات التقارير عند الاستعادة. لا يُكتفى بإضافة جداول ونسيان مسار backup/restore.

نستخدم React وFastify وmssql والمكونات القائمة. لا تحتاج هذه الوظيفة إطار موقع جديدًا أو خدمة استضافة أو اعتمادًا إنتاجيًا على Python.

لا يضاف منطق التقارير إلى ملف `apps/portal/src/main.tsx` الكبير الحالي، ولا تتحول `portal.ts` إلى ملف يجمع كل الميزات. يستخرج الغلاف المشترك للـHTTP والحماية وخدمة الملفات الثابتة تدريجيًا، مع عزل وحدات المنتجات والصور والتقارير. يبقى الاستعلام وإدارة الصور بنفس مساراتهما وسلوكهما وتغطيهما اختبارات منع التراجع.

تضبط واجهة التقارير بقاعدة assets `/reports/`، وتخدم ملفات `dist/reports` تحت هذا المسار فقط، مع دعم إعادة تحميل الروابط الداخلية مثل `/reports/movements`. لا يلتقط fallback الخاص بواجهة التقارير أخطاء `/api/reports/` ولا روابط المنتجات. خادم التطوير يوجه API للبورتال الحالي؛ بورت التطوير لا يعني إضافة بورت خدمة إنتاجي.

المشاركة بين الوحدات تقتصر على عقود البيانات ومكونات العرض المشتركة فعلًا وقراءة الهوية ووظائف الأمان الصغيرة. منطق المخزون مستقل عن React وFastify، وطبقة SQL مستقلة عن العرض، وصفحات الأدمن لا تعتمد على حالة تطبيق التقارير الداخلية. أية شاشة تقارير جديدة تضاف كوحدة واضحة مع اختبارات عقودها.

### حسابات التقارير وجلساتها

- جداول مقترحة: `report_users` و`report_sessions` و`report_settings` و`report_user_branches` و`report_saved_filters`. ترتبط بالشركة، ولا يعاد استخدام `operators` أو `photo_users` كجدول حسابات التقارير.
- الحساب: اسم مستخدم فريد ضمن نطاق الدخول، اسم ظاهر، password hash، حالة التفعيل، سياسة الفروع، وتواريخ الإنشاء/التعديل/آخر دخول. لا كلمة مرور عامة مشتركة لكل الأشخاص.
- واجهات الدخول على البورتال: `POST /api/reports/auth/login` و`POST /api/reports/auth/logout` و`GET /api/reports/auth/session`. حساب مقفل/معطل أو جلسة منتهية لا يقرأ التعريفات أو النتائج أو التصدير.
- إعدادات الأدمن: `GET/PUT /api/reporting-admin/settings` و`GET/POST /api/reporting-admin/users` و`PUT /api/reporting-admin/users/:id` وإجراء منفصل لإعادة تعيين كلمة المرور/إنهاء الجلسات. لا تسجيل ذاتي أو استعادة كلمة مرور عبر رابط عام في المرحلة الأولى.
- كلمة المرور تجزأ بخوارزمية المشروع الحالية؛ الأدمن يعين كلمة جديدة دون عرض القديمة. إعادة تعيينها أو تعطيل الحساب أو تقليل نطاق فروعه يلغي جلساته القائمة. تغيير مصدر البوابة يلغي الجلسات وcache المرتبط بالمصدر القديم.
- Cookie مستقلة باسم مثل `emoji_report_session`، HttpOnly وSameSite، وSecure مع HTTPS، ونطاق API خاص بالتقارير عند الإمكان. تحفظ في السيرفر بصمة token فقط، بمدة جلسة محددة قابلة للضبط من الإعدادات. لا تحفظ بيانات الدخول في localStorage.
- الجلسة والتحقق من التفعيل ونطاق الفروع يطبقان في hook محمي يغطي جميع routes الخاصة بالتقارير، بما فيها metadata وsaved-filters وexports. إدارة المستخدمين تبقى حصرًا على مدخل الأدمن، ولا تصبح متاحة لمستخدم تقارير بإرسال طلب مباشر.
- مخرجات عامة محدودة قبل الدخول: اسم الشركة والشعار وألوان العرض المطلوبة لصفحة الدخول وحالة إتاحة الخدمة، دون إعداد SQL أو الفروع أو المبيعات. تعطل SQL لا يمنع الأدمن من إنشاء/تعطيل المستخدمين ولا يمنع التحقق من كلمة مرور محلية؛ تعرض التقارير حالة تعذر البيانات بعد الدخول.
- تفعيل التقارير منفصل عن تفعيل الاستعلام العام للمنتجات. يعاد استخدام حماية Host/Origin وrate limits الأساسية من غلاف البورتال، وتضاف حدود لمحاولات الدخول؛ الثقة في عناوين proxy لا توسع دون إعداد صريح. لا تُنشر أي مسارات للأدمن على هذا المستمع.
- يسجل إنشاء الحساب وتغيير صلاحياته وإعادة تعيين كلمة مروره وتفعيله/تعطيله في سجل تدقيق، دون كلمات مرور أو tokens.

### الموبايل وهوية الشركة

- التصميم يبدأ بعروض 360 و390 و430 بكسل، ثم التابلت والكمبيوتر. لا تمرير أفقي للصفحة أو الأزرار الرئيسية، وتكون أهداف اللمس 44 بكسل تقريبًا أو أكثر، مع اختبار لوحة المفاتيح المفتوحة وتكبير النص.
- يستمد الاسم والشعار من الشركة وإعداداتها المعتمدة. ينطلق من هوية البورتال القائمة: الأصفر مع الدرجات الداكنة والخلفيات الفاتحة وخط IBM Plex Arabic، ويجمعها في theme tokens بدل نسخ قيم متفرقة بكل صفحة. أي ألوان إضافية لحالات الأداء تظل مقروءة ولا تعتمد على اللون وحده.
- نفس الهوية في الدخول والشريط العلوي وبطاقات النتائج والحركة والتحميل والأخطاء. الشعار يعرض بحجمه الطبيعي دون تشويه؛ أية صور/شعارات مخصصة تخزن وتتحقق وتدخل النسخ الاحتياطية مع إعداداتها.
- على الهاتف: رأس مختصر باسم الصفحة واسم الشركة، زر فلاتر واضح مع عدد الاختيارات، ملخص بسيط، ثم بطاقات الأصناف. الفلاتر والشجرة واختيار الفروع تظهر بلوحة كاملة بأزرار تطبيق وإلغاء/رجوع واضحة، مع حفظ المسودة حتى التطبيق.
- بطاقة الصنف تعرض الاسم والكود والفرع والمباع والمتبقي والتصريف، وزر تفاصيل لبقية الأرقام والحركة. جدول الكمبيوتر لا يصغر إلى خط غير مقروء على الهاتف؛ يبقى الجدول التفصيلي عرضًا اختياريًا مع تمرير داخل منطقته فقط.
- الحساب وإعدادات العرض والفلاتر المحفوظة وتسجيل الخروج يمكن الوصول لها دون مزاحمة النتائج. لا نخزن تفاصيل مبيعات حساسة offline أو نضيف service worker caching للتقارير افتراضيًا.

| 4. شاشة أداء الأصناف | فلاتر وبطاقات موبايل وجدول كمبيوتر وملخص وفرز وصفحات | الواجهة تعرض نتائج حقيقية من المصدر؛ الأصناف بلا بيع موجودة، ومجاميع كل النتائج صحيحة |
| 5. الحركة ومقارنة الفروع | تفاصيل الصنف ومقارنة بنفس النطاق | إمكانية تتبع الرصيد إلى مستنداته، والرجوع دون فقد الفلاتر؛ اختيار فرع/بعض/كل يعمل |
| 6. الحفظ والتصدير | فلاتر باسم وCSV وترحيل محلي | الفلاتر تخص مستخدم التقارير ومصدره وتعود بعد إعادة التشغيل؛ التصدير يطابق النطاق والمجاميع ويحفظ العربية والأكواد |
| 7. قبول وتشغيل | اختبارات دخول وعزل وتجربة موبايل ونسخة بناء وتغليف | حماية APIs والتحميل المباشر والتصدير، إعادة تعيين وتعطيل يلغي الجلسات، الملفات المستقلة تدخل الإصدار والنسخ والاستعادة، ولا يتأثر الاستعلام أو إدارة الصور |

نبدأ بفصل التطبيق والدخول والحسابات والهوية لأنهما أساس البوابة المطلوبة، ثم نثبت تجربة اختيار الشجرة والفروع ونربطها بالحسابات الحقيقية قبل توسيع عدد الشاشات. لا حاجة لانتظار تفسير الحالات السالبة التي طلب المستخدم عرضها صفرًا.

## 11. اختبارات القبول المحددة

- اختيار النوع «ملابس» ثم القسم «بنطلون» يعرض الأبناء الفعليين فقط؛ البحث عن «جبردين» يوضح مساره ويمكن متابعة الأبناء منه.
- اختيار قسم كامل مع صنف داخله لا يكرر الصنف. استبعاد صنف من القسم يستبعد حركته مرة واحدة. اختيار تصنيفين تحت قسمين مختلفين لا يولد تقاطعات خاطئة بينهما.
- عدم اختيار عناصر في وضع «محدد» لا يعني الكل. تغيير الأب لا يبقي ابنًا غير صالح. معرف مزور أو فرع خارج النطاق يرفضه السيرفر.
- اختيار فرعين دون الثالث لا يظهر بيانات الثالث؛ الوارد المحول من فرع غير مختار إلى فرع مختار يبقى محسوبًا، والتحويل بين مخزنين يغير المخزن ولا يخلق إجمالي مخزون للفرع.
- Z3330 / 186759 بالمنصورة، 1–27 أكتوبر: 4 افتتاح، 2 بيع، 2 نهاية. H2025 / 187754: 84 افتتاح +71 تحويل وارد −55 بيع +1 مرتجع =101.
- Z3330 بالزرقا يظهر رغم صفر المبيعات. Bd613 بالمنصورة يظهر نفاده بعد 9 أكتوبر، ولا يحسب متاحًا في الأيام الثمانية عشر الكاملة التالية.
- 13 حالة نهاية سالبة في النسخة تظهر صفرًا، وتبقى الأصول محفوظة. ورود 2 على عجز −3 لا يصنع رصيدًا موجبًا أو يوم توفر.
- حساب الافتتاح لا يتأثر بتغيير صفحة النتائج. النسب المجمعة لا تكون متوسطًا حسابيًا لنسب الصفوف، وتغيير عرض التجميع لا يغير مجموع نفس النطاق.
- آخر يوم في الفترة مشمول كاملًا، وحركة نوفمبر لا تغير رصيد 27 أكتوبر، وتواريخ ERP الخام لا تحول تلقائيًا بين UTC والقاهرة.
- حفظ فلتر لمصدر ثم تغيير المصدر لا يعيد ربط أرقامه بالخطأ. المستخدم الآخر لا يقرأ/يعدل الفلاتر المحفوظة لصاحبها.
- حساب الصور والزائر وحتى cookie الأدمن وحدها لا تقرأ API التقارير، وحساب التقارير لا يدير الصور أو مستخدمي البوابة أو SQL. لا يكفي إخفاء الروابط؛ يجرب طلب metadata وquery وexport مباشرة دون جلسة صحيحة.
- ينشئ الأدمن مستخدمين مستقلين، ولا ينتحل أحدهما فلاتر الآخر. تعطيل المستخدم أو إعادة تعيين كلمة مروره يلغي وصول جلسته المفتوحة فورًا؛ تفعيل الحساب مجددًا يحتاج دخولًا جديدًا. تغير صلاحية فروعه ينعكس على البيانات حتى مع طلب يدوي.
- تفعيل التقارير يعمل حتى مع تعطيل الاستعلام العام، والعكس. توقف SQL لا يعرض بيانات وهمية أو حديثة ظاهريًا ولا يمنع إدارة حسابات البوابة المحلية.
- `/reports/` وروابطها الداخلية تعمل بعد إعادة التحميل، وassets تحمل من المسار الصحيح داخل حزمة الإصدار؛ `/` و`/manage` يحتفظان بسلوكهما، وطلبات API المجهولة ترجع JSON مناسبًا لا HTML التطبيق.
- تجربة فعلية بعروض 360 و390 و430 و768 و1280 بكسل، مع الفلاتر والشجرة والبطاقات ولوحة المفاتيح وتسجيل الدخول والخروج؛ الاسم والشعار والألوان والخط متسقة ولا يوجد overflow للصفحة.
- نسخ SQLite وترحيله واستعادته يحافظ على حسابات التقارير والفلاتر والهوية والعملاء والإعدادات القائمة، وتلغى جلسات التقارير المستعادة.

التحقق البرمجي عند التنفيذ: الاختبارات المناسبة للحسابات وAPI ثم `npm run typecheck` و`npm run test:core` و`npm run build`، واختبارات الاستعادة/الإصدار التي تتأثر بالـmigration، وتجربة مرئية على الهاتف والكمبيوتر. هذه الخطة نفسها لا تستلزم تشغيل build أو تغيير الإصدار.

## 12. ما يدخل البداية وما يؤجل

يشمل التنفيذ الأول: تطبيق تقارير مستقل على بورت البورتال، حسابات متعددة ودخول خاص وإعدادات بالأدمن وتعيين كلمات المرور منه، تنظيم الكود حسب الوظائف، تصميم الموبايل وهوية الشركة، الشجرة والقوائم المترابطة والاختيار من أي مستوى، البحث المباشر، عدة مسارات واستثناءاتها، فرع/عدة فروع/الكل ومخازنها ضمن نطاق الحساب، أداء الكميات والأرصدة، تفاصيل الحركة، مقارنة الفروع، الفلاتر المحفوظة والتصدير.

يؤجل بوضوح: الربحية والتكلفة، اعتماد القيم المالية غير المطابقة، توقعات الطلب وقرارات التوريد الآلية، فلتر المورد قبل تثبيت معناه، تعديل تعريفات أو أرصدة ERP، والتفعيل الفعلي للدومين/النفق عند الحاجة. الحسابات المستقلة وفصل بوابة التقارير والموبايل وهوية الشركة متطلبات أساسية وليست إضافات مؤجلة. يمكن تنفيذ المرحلة الأولى مباشرة وفق هذه الخطة دون سؤال جديد عن موضع التقارير أو طريقة الدخول.

## 13. الهدف التالي: تجهيز توزيع أسبوعي من المخزن الرئيسي للفروع

### النتيجة النهائية المطلوبة

قائمة مقترحة كل أسبوع: **الصنف والوحدة، الفرع المستلم، رصيده ومعدل بيعه، احتياجه المحسوب، المتاح من مخزن الإرسال، الكمية المقترحة وسببها**. تظهر الكميات التي لم يمكن تغطيتها بسبب نقص المخزن الرئيسي، بدل تحويل العجز إلى طلب يبدو قابلًا للتنفيذ.

تبدأ القائمة كمسودة يراجعها المسؤول ويعدلها ويصدرها. لا تنشئ تحويلات داخل ERP أو تحجز بضاعة تلقائيًا في هذه المرحلة. التشغيل الأسبوعي المجدول والإشعارات وتكامل التحويلات مراحل لاحقة منفصلة، وليست أتمتة مطلوبة الآن.

### ما نؤسسه من الآن

- الاحتفاظ بهوية الصنف والوحدة والفرع والمخزن في كل حساب، حتى لو العرض مجمع بالقسم؛ التوزيع يكون على صنف/وحدة محددين ولا ينفذ على إجمالي قسم مجهول التفاصيل.
- قراءة مخازن المركز الرئيسي ضمن المصدر نفسه، مع إعداد يحدد **مخازن الإرسال الصالحة للتوزيع**. المركز الرئيسي في النسخة هو الفرع 1 وله عدة مخازن؛ لا تعتبر مخازن التالف/الموسمي أو أي مخزن آخر مخزونًا متاحًا للإرسال دون تحديد وظيفته.
- التفرقة بين رصيد تاريخي بنهاية تقرير، ورصيد حالي يستخدم للتوزيع. تعرض فترة تحليل البيع ووقت قراءة الرصيد الحالي كل على حدة؛ لا تستخدم نهاية أكتوبر لتخطيط توزيع نوفمبر.
- تثبيت حساب الوارد والصادر ومرتجع البيع والبيع الموقع وأيام التوفر. الفرع الذي نفد رصيده لا يقاس الطلب عليه بمتوسط كل أيام الشهر دون بيان مدة النفاد.
- حساب «الرصيد المتاح للإرسال» مستقل عن الرصيد الدفتري. أي حجز أو تحويل منتظر/قيد النقل يحتاج مصدرًا مثبتًا؛ غياب بيانات الحجز لا يعني وجود صفر حجز مؤكد. تظهر محدودية المقترح إذا اعتمد الرصيد وحده.
- تعريف إعدادات تشغيلية قابلة للتوسعة: الفترة المستخدمة لقياس البيع، دورة المراجعة الأسبوعية، مدة وصول التحويل، مخزون الأمان/الحد الأدنى، ومضاعفات التعبئة عند الحاجة. لا نفترض قيمًا لكل الأصناف الآن ولا نشترط ملأها لبناء شاشة الأداء.
- محرك اقتراح التوزيع المستقبلي مستقل عن قارئ SQL وعن الواجهة؛ يستقبل أرصدة ومعدلات وقيودًا ويعيد أسبابًا وأرقامًا قابلة للاختبار.

### مراحل الوصول للهدف

| المرحلة | ما نفعله | ما نراجعه مع المستخدم |
| --- | --- | --- |
| الأساس الحالي | الحسابات والدخول والشجرة وأرصدة وحركة ومبيعات ومقارنة الفروع | صحة البيانات وسهولة الموبايل؛ الحالتان المعتمدتان مرجع قبول |
| رؤية التوزيع | إظهار رصيد مخازن الإرسال بجانب رصيد ومبيعات كل فرع للصنف نفسه | مخازن الإرسال الفعلية، الأصناف المسموح بتوزيعها، ودلالات الحجز/التحويل المنتظر |
| مسودة أسبوعية محسوبة | هدف تغطية واحتياج وفائض وتخصيص كميات من الرئيسي، ثم تعديل بشري وتصدير | مقارنة المسودة بعدة دورات توزيع فعلية، مع حفظ المقترح والتعديل والسبب |
| تحسين واقتراحات أدق | مراعاة الموسم والعروض وتغير الطلب والقيود وموثوقية المعدل | هل تحقق توفرًا أفضل وتقلل الراكد؟ وما أسباب تعديل الإدارة للمقترحات؟ |
| تشغيل دوري وتكامل | إنشاء المسودة في يوم محدد وإشعار المسؤول، ثم تكامل ERP إذا طلب لاحقًا | تفويض منفصل للتوقيت والإشعارات وأي كتابة تحويلات في ERP |

### منطق مسودة التوزيع الأولى — مقترح قابل للضبط

1. يحدد المسؤول فترة قياس حديثة ومناسبة للصنف/الفرع؛ يحسب معدل البيع مع أيام التوفر وحجم العينة، ويظهر ضعف الاعتماد عند بيانات قليلة أو نفاد طويل. لا يساوي غياب مبيعات صنف جديد عدم وجود طلب عليه تلقائيًا.
2. الهدف هو تغطية الفترة حتى فرصة إعادة التوريد التالية، مع مدة وصول البضاعة ومخزون الأمان. **المراجعة كل 7 أيام لا تعني أن هدف المخزون دائمًا 7 أيام بالضبط**.
3. احتياج الفرع المبدئي = الهدف الكمي − وضع مخزونه المتوقع؛ وضع المخزون يشمل الرصيد الحالي والوارد المؤكد المنتظر والالتزامات المثبتة بحسب مصادرها وتواريخ وصولها. يوقف العد المزدوج للتحويل الصادر من الرئيسي والمسجل واردًا للفرع.
4. لا تقترح كمية سالبة، وتراعى الوحدة ومضاعفات التعبئة. الفرع ذو الرصيد السالب يعرض صفرًا وفق سياسة المستخدم، مع بقاء الأصل للحساب والتتبع.
5. توزع الكمية المتاحة بين الفروع **في حساب واحد مشترك**؛ لا يحسب كل فرع أنه يستطيع أخذ كامل رصيد المخزن الرئيسي نفسه. عند النقص تستخدم سياسة معلنة ومتفقًا عليها، مثل أولوية أقصر تغطية ثم توزيع الباقي، مع إظهار سبب التخصيص.
6. مجموع المقترح لكل صنف/وحدة/مخزن إرسال لا يتجاوز متاحه بعد الاحتياطي والالتزامات المثبتة. التقريب للتعبئة يعاد بعده التحقق من الإجمالي، وتظهر الاحتياجات غير المغطاة.
7. تعرض المسودة وقت قراءة الرصيد. قبل اعتمادها تشغيليًا يعاد فحص المتاح لأن البيع والحركات قد تستمر؛ حفظ مسودة لا يعني حجزًا فعليًا داخل ERP، ولا يكرر نفس التحويل المؤكد في مسودة ثانية.

لا نعتمد دقة نموذج التوزيع بمجرد صحة رصيد المخزون. نجاح الأساس شرط لبنائه، ثم تقاس المقترحات على التوزيع الفعلي وتعدل السياسة مع الإدارة. الأولوية الآن تنفيذ الأساس الوارد في المراحل 1–7 بالخطة، مع الحفاظ على هذه الحدود والبيانات المطلوبة للتوسع.
