# خطة برنامج الروضة لإدارة انضمام العملاء إلى واتساب

تاريخ التحديث: 30 أكتوبر 2026 — وثيقة متطلبات وتصميم ومراحل تنفيذ، وليست وصفًا لبرنامج إنتاج اكتمل بناؤه.

هذه الوثيقة هي المرجع التنفيذي الأحدث، وتستبدل القرارات السابقة المخالفة لها، خصوصًا دعم الجروب العام ودعوات الخصوصية. النطاق الحالي: جهاز Windows رئيسي واحد، حساب واتساب واحد، تسعة فروع مؤكدة، ونحو 200 عميل جديد يوميًا من حيث حمل البيانات المتوقع. هذا العدد ليس تعهدًا بمعدل إضافات يسمح به واتساب.

## 1. الهدف والقرارات الأساسية

برنامج يعمل كخدمة على جهاز السيرفر، وله لوحة تحكم عربية احترافية تُفتح من المتصفح على نفس الجهاز. يقرأ العملاء من SQL Server الحالي، ويكتشف الجديد، ويوزعهم حسب السياسة المختارة، ويضيف العملاء السابقين على دفعات يومية. يتابع النتائج والأخطاء والمغادرين ويستعيد العمل بعد إعادة التشغيل دون تكرار أعمى.

| القرار | التنفيذ المعتمد |
|---|---|
| لغة البرمجة | TypeScript للواجهة والخادم والعامل |
| الواجهة | React + Vite، وتصميم عربي RTL باستخدام Tailwind CSS ومكونات متسقة |
| الخادم | Node.js بإصدار LTS مدعوم وقت البناء + Fastify API |
| مصدر البيانات | SQL Server الحالي؛ اتصال قراءة، دون نسخ MDF/LDF أو تعديل ERP |
| موصل SQL | حزمة mssql بمحرك Tedious؛ اختبار توافقها مع إصدار SQL والبروتوكولات على الجهاز الفعلي |
| قاعدة البرنامج | SQLite محلية مع WAL وmigrations باستخدام better-sqlite3 وDrizzle |
| واتساب | whatsapp-web.js خلف WhatsAppAdapter مستقل، مع متصفح يديره عامل منفصل |
| الطابور | جداول دائمة في SQLite؛ لا Redis ولا SQL Server ثانٍ في النسخة الأولى |
| النشر | خدمة Windows تبدأ تلقائيًا، وتظل الواجهة متاحة أثناء إيقاف عمليات واتساب مؤقتًا |
| وضع التوزيع | جروبات حسب الفرع، أو عائلة جروبات عامة لكل العملاء |
| عند منع الإضافة بالخصوصية | رسالة خاصة واحدة تحتوي رابط الجروب بعد تشخيص سبب الرفض والتأكد من الوجهة |
| السجل القديم داخل الجروب | معطل حاليًا؛ فشل اختبار الإرسال على الحساب الحالي، ولا يدخل ضمن اعتماد النسخة الأساسية |

اختيار TypeScript يسمح باستخدام مكتبة واتساب مباشرة، ومشاركة تعريفات البيانات بين الواجهة والخادم. الواجهة تطبيق ويب محلي؛ لا نحتاج Electron أو تعديل ملف ERP التنفيذي في النسخة الأولى. الاختيارات التقنية هنا قرارات تصميم؛ تُثبت الإصدارات المتوافقة في lockfile بعد اختبار Windows، ولا يعتمد الإنتاج على تحديثات تلقائية غير مختبرة.

## 2. ما ثبت بالفعل وما لم يثبت

| البند | الدليل والحالة |
|---|---|
| الاتصال بالسيرفر الحقيقي | نجح اختبار UDL على localhost\SQLMOHSEN بحساب SQL، وأفاد المستخدم بظهور القواعد. Windows Authentication للحساب الحالي رُفض. لا نحفظ الباسورد في هذه الوثيقة أو في السورس |
| قاعدة ERP الحية وقراءة العملاء | يلزم اختيار الاسم الحقيقي من القواعد والتحقق من جدول العملاء والفروع وصلاحية القراءة؛ اسم ملف alrawda.mdf وحده لا يثبت اسم القاعدة المسجلة |
| مخطط البيانات | فُحصت نسخة منفصلة سابقًا؛ يلزم مقارنة المخطط والبرنامج والفروع على القاعدة الحية قبل التشغيل |
| ربط واتساب والجروبات والإضافة | نجح الربط والقراءة بعد إصلاح توافق المعرفات؛ نجحت إضافة رقم التجربة وتأكدت عضويته |
| إنشاء الجروبات | نجح إنشاء جروب اختبار، ثم إضافة العضو؛ ظهر تأخر مزامنة بعد الإنشاء وعولج بالتحقق دون تكرار الإنشاء |
| إرسال نصوص | نجح إرسال رسالتين وتأكيد الخادم؛ قد يرجع SDK دون معرف رغم وصول الرسالة، لذا نتحقق ولا نكرر آليًا |
| دعوة خاصة برابط بعد رفض الخصوصية | موثقة الإمكانات في SDK، لكن السيناريو الكامل لم يُختبر فعليًا بعد؛ شرط قبول مستقل قبل تفعيله للعملاء |
| سجل الرسائل السابق | أعاد فحص الأهلية رسالتين متاحتين، لكن الإرسال رفض بـGroup history sender is not enabled. لا يوجد نجاح إرسال أو تحقق استقبال |
| الوسائط | واجه إرسال الصورة خطأ توافق؛ لا نعتمد صور الدعوات أو الرسائل التسويقية في النسخة الأولى |

حساب sa الذي نجح به الفحص ليس اختيار التشغيل المفضل. يُجهّز حساب قراءة محدود إن أمكن. إن استُخدم حساب أوسع مؤقتًا أثناء الإعداد، فالبرنامج لا ينفذ به DDL/DML أو أوامر SQL يكتبها المستخدم، ويظهر اتساع الصلاحيات للمسؤول؛ تقييد التطبيق وحده لا يقلل صلاحيات الحساب داخل SQL Server.

## 3. تجربة أول تشغيل

معالج إعداد واضح من خطوات محفوظة، يُستكمل بعد إغلاق الصفحة أو إعادة تشغيل الجهاز. لا يبدأ إضافة أو إنشاء جروبات بمجرد فتح البرنامج.

### الخطوة 1: المسؤول وفحص الجهاز

إنشاء مستخدم إدارة محلي، وتحديد مجلد البيانات والمنطقة الزمنية Africa/Cairo. عرض فحص Node والمتصفح والمساحة وإمكانية تشغيل الخدمة. لا نفترض أن مستخدم الخدمة يملك نفس صلاحيات المستخدم الذي سجل الدخول إلى Windows. تبقى أسرار SQL وجلسة واتساب محلية ومحمية بحساب الخدمة.

### الخطوة 2: اتصال ERP

إدخال السيرفر والـInstance والاتصال واختيار القاعدة من قائمة. أزرار منفصلة: اختبار الاتصال، اختبار قراءة العملاء والفروع، ثم معاينة بيانات محدودة. تعرض الشاشة اسم القاعدة المختارة ونتيجة التحقق من المخطط وتاريخ آخر نجاح، دون عرض الباسورد. لا نربط قاعدة بمجرد تشابه الاسم.

### الخطوة 3: عرض الفروع المكتشفة

قراءة كل الفروع في البرنامج المختار وعرض الاسم والمعرف وعدد العملاء والأرقام الصالحة، مع تحديد الفروع التي ستدخل الخدمة. النسخة المفحوصة تضمنت فروعًا أخرى، لذلك لا نفعّلها كلها تلقائيًا.

الاختيار المبدئي المؤكد: المنصورة، كفر سعد، عمر أفندي، سنتر الجديدة، الزرقا، شربين، النخلة، عمر أفندي 2، وفارسكور. المعرفات المؤكدة سابقًا ضمن البرنامج 9: [39,40,41,42,45,51,56,57,60]. تُراجع مطابقة الأسماء بالمعرفات من المصدر؛ لا نعتمد ترتيب القائمة كمطابقة.

### الخطوة 4: كيف نوزع العملاء؟

خياران واضحان مع معاينة النتيجة:

1. **جروب لكل فرع:** رقم العميل يتبع الفرع الذي سجله في ERP. لكل فرع عائلة جروبات وأجزاء متتابعة مستقلة.
2. **جروب عام:** كل العملاء من الفروع المختارة يدخلون عائلة عامة واحدة، مع الاحتفاظ بفرع العميل في التقارير. تظل الأجزاء التالية عامة عند الامتلاء.

تغيير وضع التوزيع بعد بدء التشغيل يمر بمعاينة أثر على المنتظرين وتأكيد تطبيق السياسة؛ لا ينقل الأعضاء الحاليين ولا يعيد إرسال دعوات لهم تلقائيًا. تغيير الوجهة يُلغي المهام غير المنفذة التابعة لنسخة السياسة القديمة، ويعيد تخطيطها ذريًا؛ المحاولات غير المحسومة تُراجع أولًا. السياسة تحمل version مسجلة على كل مهمة.

### الخطوة 5: ربط واتساب وتحديد الجروبات الأولى

ربط الحساب بـQR ثم تحميل جروباته تلقائيًا. في وضع الفروع يظهر جدول: الفرع، الاسم الأساسي، الجروب الحالي، عدد الأعضاء، صلاحية الحساب، وحالة الربط. في الوضع العام يظهر صف واحد.

الجروبات الأولى التي أنشأها المستخدم تُختار من قائمة الجروبات الحالية، أو تُقترح تلقائيًا إذا كانت المطابقة وحيدة؛ المستخدم يراجع الربط قبل اعتماده. لا نربط بناءً على اسم متشابه أو نُنشئ جروبات مكررة. لا يلزم إعادة اختيارها عند كل تشغيل؛ نحفظ groupId الفعلي. إذا كان جروب البداية غير موجود يمكن إنشاؤه من المعالج بإجراء صريح، وهذه الإمكانية اختيارية وليست شرطًا للإعداد.

يُقترح الاسم الأساسي من اسم الجروب المختار، ويمكن تعديله للتسمية المستقبلية دون إعادة تسمية الجروب القديم. يُحفظ رقم الجزء التالي صراحة، ولا يُستنتج من حذف أرقام آخر الاسم؛ مثل «عمر أفندي 2» اسم فرع حقيقي وليس بالضرورة جزءًا ثانيًا.

يمنع اعتماد نفس الجروب لفرعين في وضع الفصل. الحساب يجب أن يكون عضوًا وأدمن وصاحب القدرات اللازمة للإضافة وإنشاء الأجزاء والحصول على رابط الدعوة. عند نقص القدرة يظهر السبب وخيار إصلاح الربط، لا نجاح وهمي.

### الخطوة 6: الأعداد والمواعيد والدعوات

تحديد دفعة العملاء القدامى، ونطاق الحد «إجمالي يومي» أو «لكل فرع»، وأوقات التنفيذ، وأيام العمل، وحد فتح الجزء التالي، ونص الدعوة ومعاينتها. زر إرسال اختبار متعمد لرقم اختبار فقط للتحقق من الدعوة، ولا يُرسل من مجرد تحرير النص.

### الخطوة 7: المراجعة والتفعيل

ملخص الاتصال والفروع والسياسة والجروبات والعدد المنتظر والمكرر وغير الصالح. عمل baseline كامل ومتسق ثم تشغيل المعاينة دون أي كتابة إلى واتساب. بعد نجاح الاختبارات التشغيلية يضغط المسؤول «بدء التشغيل». يمكن تفعيل الجديد فقط وترك دفعات القديم متوقفة.

## 4. الواجهة الاحترافية

واجهة عربية RTL بتصميم هادئ وواضح، خطوط عربية مقروءة، أرقام ومواعيد بتنسيق ثابت، ووضع فاتح/داكن اختياري. دعم شاشة السيرفر واللابتوب، حالات تحميل وفراغ وخطأ مفهومة، واستخدام بلوحة المفاتيح وتباين مناسب. لا نعتمد اللون وحده لتمييز الحالة.

| الشاشة | المحتوى والإجراءات |
|---|---|
| الرئيسية | حالة الخدمة/واتساب/SQL، آخر مزامنة، الجديد اليوم، القديم المنفذ والمتبقي، الدعوات المنتظرة، المشاكل، وموعد التنفيذ التالي |
| الفروع والوجهات | أسماء الفروع والجروبات وأجزاؤها والسعة، الجروب النشط، الربط/تغييره، إيقاف فرع، وسجل إنشاء الأجزاء |
| العملاء | بحث وفلترة بالفرع والمصدر قديم/جديد والحالة، سبب الانتظار، رقم منظف، سجل مرتبط بكل سجلات ERP المتكررة |
| الطابور | مهام الجديد والقديم والدعوات، الأولوية وموعد المحاولة وسبب التعطيل، تفاصيل النتيجة دون عرض معلومات حساسة غير لازمة |
| الدعوات | أُرسلت/تأكد تسليمها/انضم/تحتاج موافقة أدمن/انتهت/غير محسومة؛ معاينة النص وهوية الجروب وإجراء إعادة إرسال صريح |
| اتصال واتساب | QR وحالة الجلسة والأدمن، آخر تحقق، تنبيه إعادة الربط، دون كشف ملفات الجلسة |
| الجدولة والإعدادات | ساعات العمل والدفعات والسقوف وسياسة السعة ونص الدعوة والمنطقة الزمنية |
| المراجعة والتنبيهات | سبب الإيقاف والأخطاء والمحاولات غير المحسومة والتكرار وتغير الفرع/الرقم |
| الإدارة والنسخ الاحتياطي | المستخدمون والصلاحيات والسجل والإصدارات وصحة النسخ وآخر اختبار استعادة |

زر بارز دائم «إيقاف العمليات مؤقتًا» مع «حتى أستأنف» أو «حتى وقت معين». تعرض الواجهة أن المزامنة مستمرة أو متوقفة، وعدد المتراكم. لا تعرض الخدمة خضراء بينما العامل متوقف بسبب خطأ.

## 5. قراءة العملاء وتنظيف البيانات

هوية السجل المركبة: idprogramitems + idbranch + idperson. تصنيف العميل يتم بربط kindperson مع البرنامج والفرع، وليس رقم نوع ثابت لكل النظام. نقرأ الأعمدة المطلوبة فقط، مع استعلامات محددة ومعلّمة بالمعاملات ومهلة ومنع تداخل الدورات.

لا يوجد timestamp أو rowversion موثوق في جدول person بالنسخة المفحوصة، وChange Tracking غير مفعّل. البداية مسح محدود كل 30 ثانية مع بصمة للسجل ومقارنة بالمخزون المحلي؛ يُضبط الفاصل بعد قياس الحمل على الجهاز الحقيقي. لا نعتمد MAX(idperson)، ولا NOLOCK كحل اتساق، ولا Triggers على ERP. إذا أُتيح Change Tracking لاحقًا نضيف مصدرًا يدعمه مع التعامل مع انتهاء صلاحية المؤشر.

- أول baseline الناجح يميز الموجودين كعملاء قدامى، ويُحفظ ولا يُعاد تصنيف الجميع بعد إعادة التشغيل. التنفيذ ممنوع حتى اكتمال baseline. إذا لم تتوفر قراءة snapshot متسقة، تُعرض نافذة الالتقاط واحتمال تأخر تصنيف عميل أثناءها بدل ادعاء دقة لحظية.
- بعده، السجل المكتشف لأول مرة عميل جديد وله أولوية. عميل قديم استُكمل رقمه لاحقًا يدخل قائمة «قديم أصبح مؤهلًا» ويخضع لدفعة القديم؛ تصحيح رقم عميل سبق التعامل معه يذهب للمراجعة بدل إرسال لرقم جديد آليًا.
- ftel1 ثم ftel2 ثم ftel3 ثم ftel4، واختيار أول رقم موبايل مصري صالح. يمكن اعتماد رقم آخر يدويًا. لا نضيف الأرقام الأربعة تلقائيًا.
- تنظيف الأرقام العربية والفارسية والفراغات والصيغ المصرية إلى صيغة دولية موحدة. الأرقام الغامضة/الأرضية/غير الصالحة لها سبب واضح ولا تستهلك محاولات واتساب.
- لا نغيّر رقمًا أو فرعًا أو أي بيانات داخل ERP. حذف العميل من ERP لا يؤدي لإخراجه من جروب.
- فشل اتصال SQL أو قراءة جزئية لا يمسح العملاء ولا يصنع دفعة جديدة. انخفاض كبير غير متوقع في العدد أو تغير مخطط المصدر يوقف التخطيط للمراجعة.

### التكرار وتغير الفرع

في الجروب العام: كل رقم موحد له رحلة انضمام واحدة عبر جميع الفروع. في وضع الفروع: يُمنع التكرار داخل عائلة الفرع وكل أجزائها، حتى لو نفس الرقم ظهر في أكثر من سجل ERP. الرقم المشترك بين فروع مختلفة يعرض للمراجعة لتحديد فرع أساسي أو اعتماد عضوية متعددة صراحة؛ لا نضيفه للجميع تلقائيًا.

تغير فرع عميل سبق انضمامه لا ينقله تلقائيًا. تغيير الرقم لا ينقل suppression من الرقم القديم للجديد دون مراجعة. المغادر أو المُزال أو طالب عدم التواصل له suppression دائم محفوظ؛ إعادة مزامنة ERP أو إنشاء جزء جديد أو تغيير السياسة لا يعيده ولا ترسل له دعوة جديدة تلقائيًا. طلب عودة صريح يفتح إجراء مراجعة جديدًا وقد يظل واتساب رافضًا بسبب مغادرة حديثة.

## 6. رحلة العميل الجديد ودعوة الخصوصية

1. اكتشاف العميل وبياناته ثم اختيار سياسة الوجهة الحالية.
2. فحص الأهلية والموافقة المقررة في إجراءات الفرع، والتكرار وsuppression والجدول والسقوف.
3. تحديد الجزء النشط، وتحديث بياناته والتأكد من صلاحيات الحساب وسعته والعضوية الحالية، مع دعم معرفات PN/LID دون تخمين الرقم من LID.
4. تسجيل محاولة دائمة قبل الطلب ثم محاولة إضافة مباشرة واحدة بـautoSendInviteV4:false. تعطيل الدعوة الضمنية داخل SDK مقصود لأننا سنرسل الدعوة ونقيس نتيجتها كعملية مستقلة.
5. عند قبول الإضافة نتحقق من العضوية. «انضم» لا تظهر إلا بعد تأكيدها؛ قبول الطلب وحده يظهر «بانتظار التأكيد».
6. عند رفض خصوصية مؤكد ومدعوم بتفسير نتيجة SDK، ننشئ مهمة دعوة مستقلة ونرسل رسالة نصية خاصة واحدة برابط الجزء المحدد، وفق ساعات التنفيذ وسقف الحساب. لا نحوّل كل خطأ أو كل 403 مبهم إلى دعوة؛ يلزم تصنيف سبب الرفض واختباره.
7. دعوة أُرسلت لا تعني انضمامًا. نحدّث الحالة عند تأكيد الانضمام بالحدث أو مصالحة بيانات الجروب، ونراجع طلبات الانضمام إذا كان الجروب يتطلب موافقة أدمن. الموافقة عليها يدويًا في النسخة الأولى.

نص افتراضي قابل للتعديل، مع متغيرات معروفة فقط:

> أهلًا {customerName}، معاك الروضة. بناءً على موافقتك في الفرع، ده رابط الانضمام لجروب {destinationName} لمتابعة العروض: {inviteLink}

إذا الاسم مفقود تُحذف تحية الاسم بصورة سليمة. نعاين النص والرابط، ولا نضع تفاصيل مشتريات أو بيانات شخصية أخرى في الرسالة. عند طلب عدم التواصل يُسجل suppression ويوقف أي مهمة لم تنفذ. يمكن إضافة رصد رد «إيقاف» في مرحلة لاحقة، وليس مسحًا عامًا لمحادثات الحساب.

الحصول على الرابط يستخدم قدرة SDK للجروب المختار بعد فحص صلاحية الحساب. لا نجدد/نلغي رابط جروب تلقائيًا أثناء إنشاء دعوة؛ ذلك قد يبطل دعوات أخرى. إذا انقطع الإرسال بعد احتمال وصوله، تبقى الدعوة outcome_unknown ولا تعاد تلقائيًا. تحفظ هوية الرسالة إذا توفرت، ويُفرّق بين محاولة إرسال، تأكيد الخادم، التسليم، والانضمام. غياب تأكيد القراءة لا يثبت عدم الاستلام.

فشل إرسال الدعوة لا يعيد العميل إلى حلقة إضافة. لا رسائل تذكير تلقائية في النسخة الأولى. عند امتلاء الجزء بعد إرسال رابطه، لا نرسل رابطًا آخر تلقائيًا؛ تظهر حالة للمراجعة مع إمكانية إعادة دعوة صريحة إلى الجزء الجديد. مهام الدعوة التي لم تنفذ بعد يمكن تحديث وجهتها للجزء الجديد تحت قفل، مع حفظ السبب والنسخة.

## 7. العملاء القدامى والحدود اليومية

القدامى لديهم backlog ثابت مشتق من baseline، وفرز افتراضي ثابت بأول ظهور محلي ثم الهوية المركبة. تتوزع الدفعات بالتساوي النسبي/الدور بين الفروع المؤهلة حتى لا يستحوذ فرع واحد على العدد. في الوضع العام لا يتكرر الرقم بسبب الفروع.

إعداد عدد القدامى اليومي يدعم وضعين واضحين: **إجمالي لكل النظام** (الافتراضي) أو **لكل فرع**. مثلًا إجمالي 90 يعني 90 عميلًا على كل الفروع، أما 10 لكل فرع مع 9 فروع فيعني سقفًا إجماليًا ممكنًا 90. الصفر يعطل القدامى فقط؛ لا يعطل الجديد.

يُحسب الحد بعدد الأرقام الفريدة من القدامى التي بدأ لها أول إجراء خارجي في اليوم، لا بعدد المنضمين الناجحين. محاولة الإضافة ثم دعوة خصوصية لنفس العميل تحسب عميلًا واحدًا في دفعة القديم، لكن كل عملية واتساب تُحسب مستقلة في سقف إجراءات الحساب. الموجود بالفعل وغير الصالح لا يستهلكان حد دفعة جديد. حالات النتيجة المجهولة لا ترد رصيدًا تلقائيًا.

الجديد أولوية أعلى، مع تخصيص فرص للقديم عندما تسمح السقوف، ومنع تجويعه دون تنبيه. الجديد لا يستهلك حد القدامى لكنه يخضع لسقف الحساب والمواعيد والإيقاف. لا وعد بإضافة فور التسجيل: الاكتشاف يستهدف الدورة التالية، والتنفيذ حسب صلاحية الاتصال والطابور والمواعيد.

العدادات دائمة في SQLite، بمفتاح يوم محلي Africa/Cairo. إعادة التشغيل أو تغيير الإعداد أو الإيقاف لا يصفرها؛ زيادة الحد متعمدة وتُسجل، وخفضه يمنع إجراءات جديدة عند تجاوزه. فوات أيام أو تعطل الجهاز لا يضاعف دفعة اليوم التالي؛ لا تراكم حصص غير منفذة. عند انتهاء القدامى تُعرض «اكتملت دفعات العملاء القدامى» ويستمر استقبال الجديد.

## 8. إنشاء جزء جديد عند امتلاء الجروب

السعة الرسمية للجروب العادي حتى 1024 عضوًا حسب توثيق واتساب الحالي. نستخدم حد انتقال تشغيليًا قابلًا للضبط، افتراضيه 950 عضوًا شاملًا حساب التشغيل والأدمن والأعضاء؛ يمكن الاقتراب من الحد الرسمي بعد الاختبار. هامش السعة تشغيلي، وليس ضمانًا ضد تقييد الحساب.

عائلة الجروب لها baseName ثابت وcounter مستقل. مثال: «الروضة — المنصورة» ثم «الروضة — المنصورة 2» ثم «الروضة — المنصورة 3». الوضع العام يعمل بنفس الطريقة: «الروضة — العملاء» ثم «الروضة — العملاء 2». يحفظ nextCounter عند اعتماد جروب البداية، مع معاينة الاسم الناتج والتحقق من طول الاسم قبل الطلب. لا نكرر اسمًا بعد حذف جزء ولا نعيد استخدام رقم قديم.

- تحديث العدد والسعة قبل التنفيذ، مع حساب العمليات قيد التنفيذ وحجوزات الدعوات الحديثة كمؤشر تخطيط، دون اعتبار المدعو عضوًا مؤكدًا. حجوزات الدعوات لها TTL قابل للضبط ولا تمنع فرعًا للأبد؛ رابط الدعوة لا يضمن مقعدًا، وقد ينضم غير المدعوين عبر مشاركة الرابط.
- عند بلوغ حد التشغيل، أو رفض موثوق بسبب الامتلاء، نحجز مهمة create_next_group فريدة لعائلة الجروب، تحت قفل يشمل التخطيط والإضافات والدعوات الجديدة.
- ننشئ الجزء بالاسم المحسوب، ثم نتحقق من groupId والاسم وعضوية الحساب وصلاحياته وإعدادات الجروب، وبعدها فقط نجعله نشطًا. يبقى السابق في السجل مع سبب وتاريخ وقف استقبال العملاء الجدد.
- نضبط إعدادات الجزء الجديد حسب سياسة محفوظة قابلة للتحقق، لا نفترض نسخ كل إعدادات الجروب القديم تلقائيًا. البداية المقترحة: النشر للأدمن، إضافة الأعضاء للأدمن، ووصف موحد. الإعداد غير المدعوم أو الفاشل يظهر ويوقف تنشيط الجزء عند كونه إلزاميًا.
- يمكن حفظ قائمة أدمن ثابتة لإضافتها للأجزاء الجديدة بعد اختبار ذلك. إن تعذر تجهيز الأدمن المطلوبين لا نعلن الجزء جاهزًا. إنشاء الجزء قد يبدأ بحساب التشغيل وحده كما نجح في التجربة، ثم يستكمل التجهيز.
- إذا تأخرت مزامنة الجروب أو انقطع الطلب لا نعيد الإنشاء. نحتفظ بالمحاولة ونصالح النتيجة بالهوية والأدلة؛ الاسم وحده لا يحسم عند وجود أكثر من مطابق. عند الغموض يتوقف هذا المسار للمراجعة.
- لا نخرج العملاء من القديم ولا ننقلهم ولا نحذف الجروب. العضو الموجود في جزء سابق لا يُضاف للجزء الجديد لمجرد فتحه. المستقبل يتجه للجزء النشط.

تُعرض تنبيهات قرب الامتلاء والجزء الجديد، وتتوفر مراجعة أو إنشاء يدوي من اللوحة. لا نربط Community تلقائيًا ضمن النسخة الأولى.

## 9. الإيقاف المؤقت والجدولة

هناك فرق واضح بين **إيقاف إجراءات واتساب** و**إيقاف خدمة Windows**:

- إيقاف الإجراءات من اللوحة يبقي الواجهة والجلسة والمزامنة والتحقق متاحة؛ يمنع إضافة عضو أو إرسال دعوة أو إنشاء جروب جديد. يمكن اختيار إيقاف المزامنة أيضًا بشكل مستقل.
- إيقاف حساب كامل، فرع/عائلة واحدة، دفعات القديم فقط، الدعوات فقط، أو إنشاء الأجزاء آليًا. إذا توقف الإنشاء وامتلأت الوجهة تنتظر المهام ولا تذهب لوجهة غير مصرح بها.
- الإيقاف فوري قبل أي طلب جديد، لكن طلبًا خرج بالفعل لا يمكن سحبه بضمان. تنتقل العملية الجارية للتحقق من النتيجة، ولا نكررها عند الاستئناف. تعرض الشاشة عدد العمليات الجارية وقت الضغط.
- الجدولة تدعم أيام الأسبوع وعدة فترات يومية والفترات العابرة لمنتصف الليل والتوقف لتاريخ/وقت محدد. الأولوية: إيقاف بسبب مشكلة اتصال/تقييد أو شرط صلاحيات، ثم الإيقاف اليدوي، ثم الجدول، ثم السقوف والأولوية.
- الإيقاف اليدوي المفتوح لا تنهيه بداية يوم جديد. الإيقاف المحدد بوقت يستأنف عنده فقط إن بقية الشروط سليمة. تُحفظ الحالة عبر إعادة التشغيل ويظهر وقت الاستئناف القادم بتوقيت القاهرة.
- بعد الاستئناف لا تنطلق دفعة المتراكم مرة واحدة؛ تعمل التباعدات والسقوف الحالية. عند قفل المواعيد أثناء تجهيز طلب نراجعها ثانية قبل الإرسال.

تأخير العمليات وحد الدفعات وسائل تنظيم، ولا توجد قيمة ثابتة تضمن عدم الحظر. نستخدم عامل تنفيذ واحدًا وسقوفًا معلنة، مع circuit breaker عند تكرر أخطاء غير متوقعة أو ظهور قيود الحساب، دون تبديل أرقام أو محاولات التفاف آلية.

## 11. المعمارية وحدود المكونات

```text
واجهة React عربية على المتصفح
              |
        Fastify API + Login + SSE
              |
      إعدادات / قواعد توزيع / جدولة
           /              \
قارئ SQL Server        طابور SQLite دائم
      |                       |
نسخة عملاء محلية      عامل WhatsApp منفصل واحد
                              |
                 WhatsAppAdapter → whatsapp-web.js
```

الخادم يقدم الواجهة المبنية وAPI محليًا، ويستخدم SSE لتحديث الحالة. عملية عامل واتساب معزولة عن HTTP وتتعامل معه عبر IPC موثق. عامل/مكوّن المزامنة مستقل وظيفيًا عن تنفيذ واتساب. لا يحتفظ أي منهما بحقيقة حالة المهام في RAM فقط.

واجهة WhatsAppAdapter: connect، getSessionStatus، listGroups، getGroupSnapshot، resolvePhoneIds، checkMembership، addMember، getInviteLink، sendInviteText، createGroup، configureGroup، reconcileOperation. مخرجات موحدة للنجاح والرفض وعدم الحسم. تفاصيل WWebJS والـprivate modules لا تنتشر في قواعد العمل أو UI.

المحول المخصص الذي حل قراءة الجروبات في التجربة يُنقل بحذر مع اختبارات PN/LID وحقول المعرفات المتغيرة. إصلاحات التوافق تكون في المحول مع تحقق إصدار وفشل واضح، وليس تعديل node_modules يدويًا أو اعتبار تفاصيل واتساب الداخلية ثابتة. مسارات التشخيص التي تقرأ كود وحدات واتساب في المختبر لا تُنشر كـAPI إنتاج.

### هيكل المستودع المستهدف

```text
apps/web/                    # React RTL screens
apps/server/                 # API, auth, scheduling, sync orchestration
apps/whatsapp-worker/        # session, adapter, sequential execution
packages/domain/             # policies, states, types, normalization
packages/storage/            # SQLite schema, transactions, migrations
packages/erp/                # read-only SQL queries and source validation
packages/whatsapp/           # adapter contracts and compatibility handling
packages/config/             # validated configuration without credentials
scripts/windows/             # install, start, stop, backup, diagnostics
scripts/whatsapp-test/        # existing pilot isolated from production
scripts/diagnostics/          # read-only source connectivity tools
docs/                        # setup, runbooks, acceptance results
```

لا يُشارك الإنتاج profile أو قاعدة حالة المختبر؛ ترحيل جلسة اختبار إلى الإنتاج إجراء موثق بعد إيقاف النسخة القديمة، وليس تشغيل الاثنين معًا على نفس مجلد المصادقة.

## 12. التخزين والطابور ومنع التكرار

| الكيان | البيانات والقيود الرئيسية |
|---|---|
| app_settings / policy_versions | إعدادات مُصدّرة بنسخ وتواريخ النفاذ |
| operators / sessions | مستخدمو اللوحة والصلاحيات والجلسات |
| erp_sources / sync_runs | هوية المصدر وbaseline والنجاح والفشل ومؤشر الاكتمال |
| branches | هوية مركبة مرتبطة بالمصدر والبرنامج والفرع والتفعيل |
| customers / customer_phones | هوية ERP، الرقم المنظف، البصمة، أول ظهور وتصنيف قديم/جديد |
| destinations / branch_routes | عائلة الفرع أو العائلة العامة وربطها بنسخة السياسة |
| whatsapp_groups | groupId فريد، العائلة والجزء والاسم والسعة والحالة وإعدادات التجهيز |
| contact_routes / memberships | رحلة الرقم للعائلة وعضويته بكل جزء؛ قيد فريد للعائلة+الرقم وقيد groupId+الرقم |
| invitations | وجهة الدعوة ومحاولة الرسالة وحالتها، بلا خلط بين الإرسال والانضمام |
| suppressions | الرقم والنطاق والسبب والمصدر ووقت المنع؛ لا يُحذف تلقائيًا بانتهاء سجلات التشخيص |
| jobs / attempts | نوع العملية، dedupKey فريد، lease وحالة وموعد ونتيجة الطلب وأدلة التحقق |
| daily_usage / usage_reservations | حصص اليوم والحجوزات الذرية الدائمة حسب النوع والفرع واليوم المحلي |
| audit_events / notifications | تغييرات المشغل والتنبيهات وقواعد إزالة التكرار |

دورة المهمة: queued → checking → executing → verifying → succeeded، مع حالات waiting_schedule، waiting_capacity، paused، retry_wait، rejected، outcome_unknown، manual_review وcancelled_before_execution. نتيجة العميل مستقلة: joined، already_member، invitation_pending، invite_sent، invite_delivered، join_request_pending، suppressed أو requires_review.

معاملة SQLite تحجز المهمة والحصة والقفل قبل أي طلب خارجي. لا نترك معاملة مفتوحة أثناء انتظار الشبكة. لا توجد exactly-once مضمونة عبر SQL وSQLite وواتساب؛ نعتمد منع التكرار والمصالحة. عند انتهاء lease بعد تعطل executing نتحقق من الواقع قبل إعادة أي كتابة. نجاح الإضافة السابق ليس دليل عضوية حالية، وHTTP 200 وحده لا يثبت نجاحًا.

قراءات واتساب القابلة للإعادة تستخدم backoff محدودًا. الخصوصية والمغادرة وعدم وجود الرقم وفقد الأدمن لا تدخل retry غير محدود. لا نعيد إرسال دعوة أو إنشاء جروب بعد مهلة مجهولة لمجرد عدم وجود رد. حدث واتساب قد يتكرر أو يتأخر أو يفقد؛ لذلك نجمع أحداثًا خفيفة مع مراجعة دورية للجروبات المربوطة، ولا نقرأ تاريخ كل محادثات الحساب.

## 13. نشر Windows والأمان والتشغيل

- تثبيت تحت Program Files وبيانات قابلة للكتابة تحت ProgramData بمسارات ثابتة، وليس داخل فولدر ERP. تأكيد إصدار Windows ومواصفات الجهاز قبل اختيار runtime والمتصفح.
- Windows Service wrapper موثوق مثل WinSW، بإعدادات موثقة لحساب تشغيل محدود ومجلد العمل والتوقف وإعادة التشغيل. يُحسم التوافق ويُختبر في مرحلة النشر.
- SQLite على قرص محلي مع WAL وforeign_keys وbusy_timeout وmigrations وقفل نسخة التطبيق. نسخ متسق عبر آلية backup مدعومة؛ لا نسخ ملف .db وحده وهو يعمل أو وضعه داخل مشاركة شبكة.
- حماية أسرار SQL بمخزن Windows/DPAPI تحت هوية الخدمة، وحماية مجلد جلسة واتساب بـACL. عدم تضمين باسورد sa المكتشف في الشيفرة أو الأمثلة أو تقارير التشخيص. إخفاء أسرار الاتصال وروابط الدعوات في السجلات العادية.
- تشفير كلمات مرور اللوحة باستخدام تجزئة مناسبة، وجلسات HttpOnly/SameSite وحماية CSRF/Origin وتحديد معدل محاولات الدخول. تثبيت أولي على loopback فقط.
- في حال فتح اللوحة للفروع: HTTPS ومصادقة وصلاحيات وFirewall محدد للشبكة، دون تعريض SQL Server أو التحكم بواتساب للإنترنت. صلاحيات manager/operator/viewer تُجهز من البداية؛ فصل رؤية الفروع في توسعة لاحقة إذا أتيح دخول الفروع.
- إيقاف متصفح غير سليم لا يحذف الجلسة. عمليات إعادة الربط والخروج من الحساب متعمدة مع توضيح أثرها. لا تشغيل متصفحين على نفس profile أو الخدمة القديمة والجديدة معًا أثناء التحديث.
- تنبيهات داخل اللوحة عند انقطاع SQL/واتساب وفقد الأدمن وقرب الامتلاء وفشل إنشاء جزء وتراكم الطابور أو عدم حصول القديم على فرص. لا نرسل تنبيهات خارجية لآخرين دون إعداد وجهتها وتفعيلها.
- نسخ احتياطي يومي متسق لقاعدة التطبيق وإعدادات قابلة للاستعادة؛ أسرار وجلسات الدخول لها سياسة منفصلة محمية. استعادة نسخة قديمة تبدأ reconciliation ووضع preview حتى لا تعيد عمليات وقعت بعد تاريخ النسخة.
- مراجعة تبعيات Puppeteer ومعالجة التنبيهات المعروفة قبل الإنتاج، واختبار تحديثات SDK/WhatsApp. لا audit fix --force أو تحديث صامت أثناء التشغيل.

## 14. مراحل التنفيذ والمخرجات

| المرحلة | العمل | معيار التسليم |
|---|---|---|
| 0 — تثبيت معلومات البيئة | تحديد قاعدة ERP الحقيقية واختبار SELECT محدود، مقارنة المخطط والفروع، Windows/RAM/SQL versions، وحساب الخدمة | تقرير اتصال ومخطط بلا أسرار، دون تعديل ERP |

| 3 — التنفيذ الأساسي | العامل وWhatsAppAdapter والطابور والأولوية والحدود اليومية والتوقيت والإيقاف والتعافي | تجربة أرقام موافقة محدودة؛ تحقق عضوية ومنع تكرار بعد تعطل |
| 4 — دعوات الخصوصية | سبب الرفض الموثوق ورابط الجروب ونص الدعوة وACK ومتابعة الانضمام | رقم تجربة يمنع الإضافة يتلقى دعوة واحدة وينضم؛ لا دعوة ثانية بعد مهلة أو إعادة تشغيل |

## 15. اختبارات القبول الرئيسية

1. أول تشغيل يعرض كل الفروع المكتشفة، ويختار فقط المعتمدة؛ الفروع غير المختارة لا تنتج مهام.
2. اختيار per_branch يوجه كل عميل لفرعه الصحيح؛ global يوجه الجميع للعائلة العامة، والرقم المتكرر بين الفروع ينتج رحلة واحدة.
3. الجروبات الأولى تُحمّل وتُراجع وتُحفظ بالهوية؛ جروبان بنفس الاسم لا ينتج عنهما ربط تلقائي خاطئ، وإعادة التشغيل لا تعيد المعالج من الصفر.
4. عميل جديد يُكتشف في الدورة التالية عند سلامة الاتصال، ويظهر سبب أي انتظار. استكمال رقم عميل قديم وتغيير فرعه أو رقمه لا يصنفه عميلًا جديدًا بلا ضابط.
5. إعادة المزامنة أو انتهاء الخدمة أثناء الإضافة لا تعيد إضافة نجحت؛ فقدان ACK لا يطلق رسالة ثانية.
6. حد القديم الإجمالي 10 لا يصبح 90 بسبب وجود تسعة فروع. وضع لكل فرع يحسب بشكل منفصل، والنوع ظاهر في الواجهة.
7. استئناف بعد منتصف الليل أو تغيير الحد أو إعادة التشغيل لا يصفر عداد اليوم، ولا يجمع حصص أيام فائتة؛ تختبر الفترات الليلية وتوقيت القاهرة.
8. رفض الخصوصية المؤكد يرسل دعوة واحدة بالرابط الصحيح؛ رفض بسبب مغادرة أو عدم وجود الرقم أو غياب الأدمن أو سبب مبهم لا يرسلها.
9. إرسال دعوة لا يظهر كانضمام؛ الانضمام بالرابط وطلب موافقة الأدمن وحالة دعوة مجهولة لها نتائج منفصلة قابلة للمراجعة.
10. وصول العدد للحد أو امتلاؤه أثناء الإضافة ينشئ جزءًا واحدًا باسم وcounter صحيحين. اسم فرع ينتهي برقم لا يتلف، والجزء غير الجاهز لا يصبح نشطًا.
11. رابط أُرسل لجزء امتلأ لاحقًا لا يؤدي لإرسال خاص متكرر تلقائيًا؛ الدعوة غير المنفذة تستخدم الوجهة الحالية بعد التحقق.
12. عضو في جزء قديم لا يضاف للجزء الجديد، والمغادر أو طالب الإيقاف لا يعود بسبب baseline أو تغيير سياسة.
13. الإيقاف يمنع الإضافة والدعوة والإنشاء ويُبقي اللوحة متاحة؛ العملية التي خرجت قبل الإيقاف تُراجع دون ادعاء إلغائها.
14. تغيير وضع التوزيع أو ربط الجروبات لا ينقل أعضاء ولا يترك مهام السياسة القديمة قابلة للتنفيذ؛ الحالات غير المحسومة لا تُفقد.
15. فقد SQL أو واتساب أو الأدمن يوقف المسار المناسب، واستعادة الاتصال لا ترسل المتراكم كله فورًا.
16. استعادة backup قديم تبدأ بالمصالحة والمعاينة، وتحافظ على حالات المغادرة والحصص والمحاولات غير المؤكدة؛ الأسرار لا تظهر في التصدير.
17. الواجهة RTL وتوضح معنى الأعداد والحالة وآخر مزامنة والتشغيل القادم؛ الأزرار التي تكتب إلى واتساب محمية بالمصادقة والتحقق من الطلب.

## 16. إضافات مفيدة وترتيبها

**ضمن النسخة الأولى:** معاينة قبل التشغيل، إيقاف عام وفرعي، تنبيهات داخلية، تقرير يومي بالأعداد والأسباب، قائمة عدم الإضافة/التواصل، تصدير نتائج منقح إلى CSV، فحص صحة المصدر والجلسة والسعة، وسجل محاولات قابل للبحث. تصدير CSV يعالج القيم التي قد تتحول لصيغ عند فتحها في Excel.

**بعد استقرار التشغيل:** حسابات دخول مستقلة للفروع بصلاحيات محددة، معالجة ردود إلغاء التواصل، مراجعة طلبات الانضمام من اللوحة، مزامنة Change Tracking إذا أتيحت، قوالب متعددة حسب الفرع، واستيراد قائمة استثناءات. أي إرسال عروض أو حملات أو رسائل ترحيب جماعية ميزة مستقلة بحدودها واختباراتها.

**مؤجل لعدم نجاح الاختبار الحالي:** مشاركة السجل القديم داخل نفس الجروب، الصور والوسائط، وأتمتة Communities. لا نعرضها للمستخدم كقدرة مضمونة أو نعوّض فشل السجل بإعادة نشر القديم دون طلب.

## 17. الخطوة التالية عند بدء التنفيذ

تنفيذ المرحلتين 0 و1: تثبيت اسم قاعدة ERP وصلاحية SELECT الفعلية، ثم أساس TypeScript ولوحة RTL ومعالج الإعداد وSQLite بوضع preview. بعدهما مزامنة العملاء ثم العامل والدعوات والأجزاء. لا نحتاج تغيير ERP التنفيذي أو الوصول لملفات MDF الحية.

المعلومات المتبقية تُجمع خلال الإعداد: اسم القاعدة الفعلي وإصدار SQL وWindows ومواصفات الجهاز، اختيار per_branch أو global، هويات الجروبات الأولى وأسماؤها الأساسية، حجم دفعات القديم ونطاقه، ساعات العمل والسقوف، وقائمة الأدمن المطلوبة للأجزاء الجديدة. لا تمنعنا هذه التفاصيل من بناء الأساس والواجهة الآن، لكنها مطلوبة قبل live.
